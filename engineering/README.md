# 工程文件

給開發這個專案的人和 agent 用的工作文件。給使用者看的文件在 `docs/`。

| 文件 | 放什麼 | 什麼時候讀 |
|---|---|---|
| [architecture.md](architecture.md) | 系統怎麼建：元件、資料流、測試接在哪裡 | 改架構、測試或 migration 之前 |
| [specs/](specs/) | 產品規格 v1.1 與九份增補：每個功能要做什麼、不做什麼、怎麼算完成 | 做某個功能之前，讀票檔列出的章節 |
| [decisions/](decisions/) | 每個難以回頭的選擇一個檔，寫當時的原因 | 提議改掉這類選擇之前 |
| [tickets/](tickets/) | 每張票一個檔，一張票是一件使用者可以做的事 | 挑下一件工作時 |
| [contracts/](contracts/) | Core 與 Agent 之間的訊息契約，以及兩邊測試共用的資料 | 改通道訊息、授權憑證或帳本格式之前 |

其他相關位置：

- `/DESIGN.md` 是視覺與互動基準，`/design/` 是設計階段的工作檔。
- `/docs/research/` 是參考專案的原始碼研究報告。
- `/AGENTS.md` 是工作規則。

## 怎麼使用這些文件

- **進度就是票檔的位置。** 還沒開始的票在 `tickets/`，進行中的在 `tickets/doing/`，完成的在 `tickets/done/`。一張票的 `Blocked by` 都在 `done/` 時就可以開始。票號是名字，不是順序。
- **交付一張票的變更，同時把票檔移到 `done/`。**
- **需求改變時先改規格**，再改引用到那條需求的票，最後才改程式。新增或拆分票時更新 `tickets/traceability.json`，每條需求只有一張擁有票。
- **發現問題但這次不修，就寫成票**，或寫進負責那張票的 `## Notes`。
- **決策紀錄核定後不改內容。** 之後的決定寫一份新的，舊的只改狀態行。
- **票檔是驗收條件的唯一來源。** GitHub issue 的內文從票檔產生，不在 issue 另寫一套。
