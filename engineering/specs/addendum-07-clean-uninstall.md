# 規格增補 07｜主機變更帳本與完全移除

- **狀態**：已核定。2026-11-08 使用者要求解除安裝要能刪乾淨、跟沒裝過一樣，連帶裝的東西也要清掉。
- **位置**：本增補是第 55 章，接在增補 06（第 54 章）之後。v1.1 原檔與 `SHA256SUMS.txt` 不改。需求 ID 以 `UNX-` 開頭，驗收案例從 `T-244` 開始編號。
- **細化的既有需求**：INS-012、INS-014、UN-001～UN-005、P-11（「解除安裝有精準清單」）。UN-004「只清除可證明屬於自己的變更」照舊；本章補上「怎麼證明」與「完全移除」這個選項。
- **不變的部分**：預設仍是 UN-001「移除平台但留下應用」。完全移除是使用者明確選擇的另一種模式。

## 55.1 主機變更帳本

要做到「跟沒裝過一樣」，前提是平台知道自己對主機做過什麼。所以從安裝的第一步起，平台對主機的每一個變更都寫進這台主機的變更帳本。

- **誰寫**：主機上的變更一律經高權限執行器（engineering/architecture.md），由執行器在變更前後寫帳本。沒有寫進帳本的變更，執行器拒絕執行。
- **記什麼**：每筆記錄變更的對象、類型、變更前的狀態、變更後的狀態、時間、哪個工作造成的。

| 對象 | 變更前狀態要記的內容 |
|---|---|
| 套件 | 安裝前有沒有這個套件、原本版本；套件來源（apt／dnf 的 repo 與簽章金鑰）是不是平台加的 |
| 檔案與目錄 | 原本存不存在、原本內容的雜湊與備份、擁有者與權限 |
| 設定值 | 檔案路徑加上鍵，例如 `/etc/docker/daemon.json` 的 `log-opts`、`/etc/systemd/journald.conf` 的 `SystemMaxUse`，以及原本的值 |
| systemd 單元 | 原本存不存在、原本是否啟用與執行中 |
| 使用者與群組 | 原本存不存在、原本的群組成員 |
| 防火牆 | 平台自己的表或鏈、平台加進既有工具的規則 |
| 容器、網路、儲存卷、映像 | 是平台建立的，還是安裝前就有、後來接管的 |
| 其他 | sysctl、核心模組、掛載（fstab）、cron 與 timer、CA 憑證、DNS 設定 |

- **三種擁有權**：
  - **平台安裝**：安裝前不存在，由平台建立。
  - **平台修改**：安裝前就存在，平台改過內容或狀態。
  - **既有**：安裝前就存在，平台沒有動過，或只讀取。
- **安裝前快照**：安裝時記一份主機摘要，包括已安裝套件清單、已啟用的 systemd 單元、監聽中的 Port、使用者與群組、防火牆規則數、平台會寫入的路徑是否存在。移除後拿來比對。
- **帳本的保存**：每台主機在本機保存一份（Agent 資料目錄，只有 root 可讀），Core 也保存一份。主機連不上 Core 時，仍能只靠本機那份移除。
- **使用者自己改的**：平台寫過的檔案後來被使用者手動改過時（內容雜湊和帳本記錄的不同），移除時不直接還原或刪除，列出來讓使用者選擇。
- **接管與外部資源**：接管的既有資源標「既有」，移除時不刪除（44.2）。

## 55.2 三種移除方式

| 方式 | 平台本身 | 平台建立的應用與資料 | 平台順帶安裝的東西（引擎、套件、設定） |
|---|---|---|---|
| 只移除平台（預設，UN-001） | 移除 | 保留，照常運作 | 保留，因為應用還在用 |
| 移除平台與它建立的應用 | 移除 | 逐項選擇保留、匯出或刪除 | 保留 |
| 完全移除 | 移除 | 逐項選擇保留、匯出或刪除 | 帳本證明是平台安裝、而且沒有其他東西在用的，移除；平台修改過的既有設定，還原成安裝前的值 |

完全移除時，帳本裡的每一筆依擁有權處理：

| 擁有權 | 處理 |
|---|---|
| 平台安裝，沒有其他東西在用 | 移除。例如平台裝的 Docker、Zentinel、cloudflared、NVIDIA Container Toolkit、平台加的套件來源與金鑰、`hazelminx` 使用者、平台的 systemd 單元與 timer、平台的防火牆表、平台寫的設定檔 |
| 平台安裝，但後來有其他東西在用 | 不自動移除，列出誰在用讓使用者決定。例如平台裝的 Docker 上跑著使用者自己用 CLI 建的容器 |
| 平台修改 | 還原成安裝前的值。例如 journald 的上限、`daemon.json` 的 `log-opts`、sshd 設定、sysctl |
| 平台修改，但使用者後來又改過 | 不還原，列出差異讓使用者選擇：還原成安裝前、保留現在的值 |
| 既有 | 不動 |

- **使用者資料一律另外確認**：應用、資料庫、儲存卷、模型庫、備份、上傳的檔案，即使選了完全移除，也要在清單裡逐項勾選才刪除，預設是保留。每一項都可以先匯出。刪除要輸入主機名稱確認。
- **移除的順序**：先停止依賴者，再移除被依賴的。例如先停止並移除應用，再移除 Zentinel 與引擎，最後移除 Agent 與高權限執行器。
- **維護缺口（UN-003）**：保留的應用失去哪些維護，例如憑證續期、備份、WAF、磁碟保護，在預覽中逐項列出。

## 55.3 範圍：一台主機或整個平台

- **移除一台主機**：只清這台主機的帳本內容與它的 Agent，並從 Core 移除這台主機。其他主機不受影響。
- **移除整個平台**：每台主機依序完成移除，最後移除 Core。主機連不上時，提供一份離線移除包：Agent 的 CLI 加上這台主機的帳本，在主機上執行 `sudo hazelminx uninstall --mode=<方式>` 就能完成，結果寫在本機報告。

## 55.4 預覽、執行與驗證

- **預覽**：執行前依 55.2 的規則列出每一項會被移除、還原、保留或需要決定，並寫出原因與帳本記錄的時間、造成的工作。
- **執行**：是一個工作，逐項回報結果。單一項失敗不中斷整個移除，失敗項目列在最後的報告裡。
- **驗證**：移除完成後，拿安裝前快照比對主機現況，報告寫出：
  - 與安裝前相同的項目。
  - 不同的項目，以及原因（使用者選擇保留、有其他東西在用、使用者改過、移除失敗）。
  - 需要重新開機才會完全生效的項目，例如移除的核心模組。
- **報告的保存（UN-005）**：介面消失後，報告留在主機的 `/var/log/hazelminx-uninstall-<時間>.txt`，只有 root 可讀，以及 `hazelminx uninstall --report` 可以再看一次。報告不含機密值。
- **不能保證的部分**：套件管理器在移除時順帶移除或保留的相依套件，依發行版的行為；這些在報告中照實列出，不宣稱「完全相同」。

## 55.5 要求

| ID | 誰可以做什麼與必要行為 | 可檢驗的完成條件 |
|---|---|---|
| UNX-001 | 平台對主機的每個變更都寫進變更帳本。 | 依 55.1 記錄對象、類型、變更前與變更後的狀態、時間與工作；沒寫進帳本的變更，高權限執行器拒絕執行；帳本在主機本機與 Core 各一份。 |
| UNX-002 | 平台在安裝時記錄安裝前快照。 | 內容依 55.1；移除後可以拿來比對。 |
| UNX-003 | 管理員可以從三種移除方式中選擇，並看到逐項預覽。 | 依 55.2 的表處理每一筆；預設是只移除平台；預覽寫出每一項的處理方式、原因與帳本來源。 |
| UNX-004 | 完全移除只移除帳本證明是平台安裝、而且沒有其他東西在用的項目，並把平台改過的既有設定還原成安裝前的值。 | 平台安裝但仍在被使用的、使用者後來改過的，列出讓使用者決定；既有的不動；不沿符號連結刪除其他路徑（UN-004）。 |
| UNX-005 | 使用者資料只有在逐項勾選後才刪除。 | 預設保留；每項可以先匯出；刪除要輸入主機名稱確認。 |
| UNX-006 | 管理員可以移除一台主機，或移除整個平台；主機連不上時可以用離線移除包。 | 移除一台主機不影響其他主機；離線移除包只靠本機帳本就能完成，並寫出本機報告。 |
| UNX-007 | 移除後平台比對安裝前快照並留下報告。 | 報告列出相同、不同（含原因）與需要重開機的項目；保存在 `/var/log/hazelminx-uninstall-<時間>.txt` 並可用 CLI 再看；不含機密值。 |

## 55.6 驗收案例

| ID | 情境 | 預期 |
|---|---|---|
| T-244 | 在一台全新的 Debian 主機安裝平台（平台順帶裝了 Docker 與 Zentinel），部署一個應用，接著選完全移除，應用與資料都勾選刪除。 | 報告寫出與安裝前快照相同；Docker、Zentinel、平台的 apt 來源與金鑰、`hazelminx` 使用者、平台的 systemd 單元與防火牆表都不存在；監聽中的 Port 與安裝前相同。 |
| T-245 | 安裝前主機已有 Docker 與一個使用者自己的容器，journald 已設 `SystemMaxUse=500M`。安裝平台後選完全移除。 | Docker 與使用者的容器都還在；journald 維持 500M；平台加的 `daemon.json` `log-opts` 被還原成安裝前（不存在）。 |
| T-246 | 平台裝了 Docker，之後使用者用 CLI 自己建了一個容器。選完全移除。 | Docker 沒有被移除，預覽寫出「有使用者自己建的容器在用」，讓使用者決定。 |
| T-247 | 平台寫過 `/etc/ssh/sshd_config.d/50-hazelminx.conf`，使用者後來手動改了這個檔案。選完全移除。 | 這個檔案列為「使用者改過」，讓使用者選還原或保留，沒有被直接刪除。 |
| T-248 | 選完全移除，但沒有勾選刪除 shop-db 的資料。 | shop-db 的資料目錄與儲存卷都還在；報告列出它們的位置與「使用者選擇保留」。 |
| T-249 | 移除整個平台時，hazel-jp-02 連不上。 | 其他主機照常完成；jp-02 產生離線移除包；在 jp-02 上執行後完成移除並寫出本機報告。 |
| T-250 | 嘗試在沒有經過高權限執行器、也沒有寫帳本的情況下修改主機設定。 | 執行器拒絕；稽核紀錄有這次拒絕。 |
| T-251 | 移除過程中，移除 Zentinel 這一項失敗。 | 其他項目照常完成；報告最後列出 Zentinel 移除失敗與原因；報告沒有宣稱與安裝前相同。 |

## 55.7 不納入的部分

- 還原平台安裝前就已存在、但與平台無關的系統變更。
- 移除使用者在平台外自己裝的套件或容器。
- 保證發行版套件管理器自動處理的相依套件與安裝前完全一致。
