# 規格增補 06｜1Panel 商店範本的轉換，以及應用的網路與資料掛載

- **狀態**：2026-11-08 使用者要求以下幾件事：
  - 從 1Panel 商店安裝時，要處理範本，包括網路。
  - 已安裝的應用可以加進網路、改資料掛載點；安裝時能設，之後也能隨時改。
  - 54.1 的網路模型（每個應用一個網路、平台管理的共用服務各自一個網路、不使用全部互通的共用網路），2026-11-08 使用者核定採用。
- **位置**：本增補是第 54 章，接在增補 05（第 53 章）之後。v1.1 原檔與 `SHA256SUMS.txt` 不改。需求 ID 以 `APX-` 開頭，驗收案例從 `T-234` 開始編號。
- **細化的既有需求**：APP-001、APP-003、APP-004、APP-005、APP-007、APP-008；CTR-007；ENV-008；增補 03 的 ROB-003、ROB-012；增補 04 52.4 的覆寫層。
- **依據**：1Panel 官方商店 `1Panel-dev/appstore` 的範本（例如 `apps/nextcloud/35.0.2`、`apps/wordpress/7.1.4`）。範本的共通寫法：
  - 每個服務都加入外部網路 `1panel-network`（`external: true`）。
  - 容器名稱寫成 `container_name: ${CONTAINER_NAME}`。
  - Port 寫成 `${PANEL_APP_PORT_HTTP}:80`，對主機所有位址開放。
  - 資料寫在範本目錄底下的相對路徑，例如 `./data:/var/www/html`。
  - 需要資料庫的應用，在 `data.yml` 用 `type: apps` 加 `type: service` 讓使用者選另一個已安裝的應用，再把那個應用的容器名稱填進 `PANEL_DB_HOST`。這要靠所有應用都在同一個 `1panel-network` 裡才連得到。
  - 標籤 `createdBy: "Apps"`。

## 54.1 網路模型

- **不使用一個所有應用共用的網路**：共用網路讓任何一個應用都連得到所有資料庫與 Redis，一個應用被入侵，整個網路裡的服務都碰得到；也違反第 40 章「不能只信任整段 Docker 網路」。
- **每個應用有自己的網路**：名稱是 `<應用名稱>_default`，應用自己的服務（例如 nextcloud 與它專用的資料庫）都在裡面。
- **平台管理的共用服務各自一個網路**：例如重用的資料庫 shop-db 在 `hzx-db-shop`，Ollama 在 `hzx-ollama`。要用它的應用由平台接上那個網路，不需要把所有東西放在一起。
- **Zentinel 連應用**：Zentinel 是主機上的 systemd 服務，經平台配發的受控本機回送 Port 連到應用（19.2），不加入應用的網路。
- **不同主機、不同部署單元之間**：用增補 04 的內部位址，不靠共用網路。
- **相容模式**：使用者可以對單一應用勾選「加入 1panel-network」，例如它要連一個仍由 1Panel 管理的服務。勾選前提示加入後會跟所有 1Panel 應用互通。平台不會為了這個主動建立 `1panel-network`；主機上本來沒有時，選項停用並寫出原因。

## 54.2 安裝 1Panel 範本時的轉換

平台不改商店的原始範本。以下調整全部寫在平台的覆寫層（增補 04 的 52.4），安裝預覽並排列出「範本原本」與「平台調整」。

| 範本寫法 | 平台怎麼處理 |
|---|---|
| `networks: [1panel-network]`，外部網路 | 改成應用自己的網路；只有使用者勾選相容模式時才保留 |
| `container_name: ${CONTAINER_NAME}` | 填成 `<應用名稱>` 或 `<應用名稱>-<服務>`；同一個引擎環境已有同名容器時，安裝前擋下 |
| `${PANEL_APP_PORT_*}:<容器 Port>` | 預設改成只綁 `127.0.0.1`，由 Zentinel 對外（網域與憑證在安裝表單設定）。使用者選「直接對外」時才綁所有位址，並依 ENV-008 寫入攔截規則與外部實測 |
| `./data`、`./conf` 這類相對路徑 | 依每個掛載在安裝表單選的位置換成絕對路徑。預設是所選磁碟的預設位置 `<掛載點>/hazelminx/apps/<應用名稱>/`，第一次用才建立 |
| `type: apps` 與 `type: service` 選的相依服務，填進 `PANEL_DB_HOST` 等變數 | 選項改為列出平台管理的資料庫與服務。選既有的，就把它的內部位址填進變數，並把應用接上它的網路（例如 `hzx-db-shop`）；選新建專用的，就建在應用自己的網路裡 |
| 時區預設 `Asia/Shanghai` | 改成主機設定的時區 |
| `labels: createdBy: "Apps"` | 保留，另外加上平台的服務 ID 標籤（ROB-006） |
| `scripts/` 底下的安裝或升級腳本 | 依 APP-009 列出內容與需要的權限，批准後才執行 |

- **預檢**：轉換後的設定要能通過 Compose 解析，所有掛載的位置空間足夠，Port 沒有衝突。任一項失敗，不留下半套服務（APP-003）。
- **範本更新（APP-007）**：新版範本進來時重新套用同一套轉換，並保留使用者改過的網路與掛載，不被範本預設值蓋掉。差異預覽另外標出範本本身改了什麼。

## 54.3 安裝時與安裝後可以改的

| 項目 | 安裝時 | 安裝後 |
|---|---|---|
| 加入網路 | 可以勾選應用自己的網路以外，還要加入哪些網路 | 隨時加入或移出。立即生效，不必重建容器（`docker network connect`／`disconnect`），同時寫進覆寫層，之後部署或更新也保留 |
| 移出網路 | — | 應用自己的網路不能移出；移出相依服務的網路前，先列出會斷掉的連線（ROB-003） |
| 資料位置 | 每個掛載各自選位置，可以用資料夾選擇器 | 「改位置」有兩種方式，見下方 |

改資料位置：

- **搬移資料**（預設）：
  1. 檢查新位置的空間。
  2. 服務照跑時先複製。
  3. 停止應用。
  4. 最後同步，核對檔案數與大小。
  5. 改掛載並啟動，通過健康檢查。
  6. 舊資料預設保留 7 天後才刪除，期間可以一鍵改回。
- **只改掛載點**：新位置已經有資料時使用。不複製，改完直接重啟；啟動前檢查新位置不是空的，空的時候要再確認一次。
- **預估停機**：畫面寫出預估的停機時間，只有停止到啟動那段會停機。
- **Docker 儲存卷**：可以改成主機上的資料夾，也是用搬移資料的方式；反過來也可以。

## 54.4 接管既有 1Panel 安裝的應用

- **原地保留**：已經由 1Panel 安裝的應用、`1panel-network` 與它們的資料位置都原地保留，控制者標「1Panel」，平台只讀（ROB-012）。
- **一個一個轉換**：使用者可以把單一應用轉成平台管理。轉換是一個變更計畫，預覽要改的網路、容器名稱、Port 綁定與資料位置；資料位置預設不動。
- **轉換的順序**：有相依關係的應用，例如 WordPress 用 1Panel 的 MySQL，預檢會列出相依服務還在 1Panel 管理時，應用要用相容模式暫時留在 `1panel-network`，等相依服務也轉換後再移出。
- **回復**：轉換失敗或使用者在觀察期內選回復時，恢復原本的容器設定與網路。

## 54.5 要求

| ID | 誰可以做什麼與必要行為 | 可檢驗的完成條件 |
|---|---|---|
| APX-001 | 平台安裝的每個應用都有自己的網路，不預設加入任何共用網路。 | 應用的服務都在 `<應用名稱>_default`；沒有勾選相容模式時，不加入 `1panel-network`；平台不主動建立 `1panel-network`。 |
| APX-002 | 管理員從 1Panel 商店安裝時，平台依 54.2 轉換範本。 | 54.2 表中每一列都有處理；調整只寫在覆寫層；安裝預覽並排列出範本原本與平台調整；預檢失敗不留下半套服務。 |
| APX-003 | 管理員可以讓應用重用平台管理的資料庫等相依服務。 | 選項列出平台管理的服務；選既有的時，變數填入它的內部位址，應用接上它的網路；選新建專用的時，建在應用自己的網路。 |
| APX-004 | 管理員安裝時可以選要加入的網路，以及每個掛載的位置。 | 每顆資料磁碟有預設位置，第一次用才建立；可以用資料夾選擇器；空間不足在安裝前擋下。 |
| APX-005 | 管理員可以隨時把應用加入或移出網路。 | 立即生效，不必重建容器；寫進覆寫層，部署或更新後仍保留；應用自己的網路不能移出；移出相依服務的網路前列出會斷掉的連線。 |
| APX-006 | 管理員可以隨時改應用的資料位置。 | 依 54.3 的搬移資料或只改掛載點；寫出預估停機；舊資料預設保留 7 天，期間可以一鍵改回；儲存卷與主機資料夾可以互轉。 |
| APX-007 | 範本更新時，使用者改過的網路與掛載不被蓋掉。 | 重新套用 54.2 的轉換；預覽分開標出範本本身的變更與平台調整。 |
| APX-008 | 管理員可以把既有的 1Panel 應用一個一個轉成平台管理。 | 依 54.4 原地保留、預覽、處理相依順序；失敗或回復時恢復原本的設定與網路。 |

## 54.6 驗收案例

| ID | 情境 | 預期 |
|---|---|---|
| T-234 | 從 1Panel 商店安裝 Nextcloud 35.0.2，主機上沒有 `1panel-network`。 | 安裝成功；容器在 `nextcloud_default`；主機上沒有出現 `1panel-network`；預覽並排列出 `networks`、`container_name`、Port、`./data` 與時區的調整。 |
| T-235 | 安裝時 HTTPS Port 用範本預設的 40069，網域設 `cloud.example.tw`。 | 容器的 443 只綁在 `127.0.0.1`；從外部連主機的 40069 連不到；`https://cloud.example.tw` 經 Zentinel 可以開啟。 |
| T-236 | 安裝 WordPress 7.1.4，資料庫選既有的 shop-db（平台管理，網路 `hzx-db-shop`）。 | `WORDPRESS_DB_HOST` 是 shop-db 的內部位址；wordpress 容器同時在 `wordpress_default` 與 `hzx-db-shop`；連得到 shop-db；連不到其他應用的資料庫。 |
| T-237 | 已安裝的 nextcloud 加入網路 `hzx-ollama`，再移出。 | 加入與移出都沒有重建容器；加入後連得到 Ollama，移出後連不到；之後更新 nextcloud，網路設定照舊。 |
| T-238 | 嘗試把 wordpress 移出 `hzx-db-shop`。 | 移出前列出「wordpress → shop-db 的連線會斷掉」，確認後才移出。 |
| T-239 | 把 nextcloud 的 `/data` 從 `/mnt/data` 搬到 `/mnt/fast`（212 GiB），搬移期間持續上傳檔案。 | 先複製時服務照常；只在最後同步時停機；檔案數與大小核對相符；啟動後新舊上傳的檔案都在；舊資料保留 7 天，期間可以一鍵改回。 |
| T-240 | 範本出了新版，新版把 `./data` 改成 `./data/app`；使用者之前已把資料位置改到 `/mnt/fast`。 | 預覽分開列出範本的變更與平台調整；更新後資料位置仍是 `/mnt/fast`。 |
| T-241 | 主機上已有 1Panel 安裝的 WordPress 與 MySQL，把 WordPress 轉成平台管理，MySQL 仍由 1Panel 管理。 | 預檢寫出 MySQL 仍由 1Panel 管理，WordPress 要用相容模式暫時留在 `1panel-network`；轉換後 WordPress 照常連得到 MySQL；回復後恢復原本的容器設定。 |

## 54.7 不納入的部分

- 修改 1Panel 商店的原始範本或把轉換結果回傳給上游。
- 在主機上沒有 `1panel-network` 時代為建立它。
- 跨主機搬移應用（由第 44 章的遷移處理）。
