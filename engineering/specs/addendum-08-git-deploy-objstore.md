# 規格增補 08｜既有 Compose 專案的部署相容、分支觸發與物件儲存

- **狀態**：已核定。2026-11-08 使用者要求：照自己 GitHub 上的部署方式（repo 裡放 `docker-compose.yml`，主機上拉下來 `docker compose up -d`）找出會遇到的問題；推到某個分支就自動部署，而且可以選要聽哪個分支；除了資料庫，也要有物件儲存。
- **位置**：本增補是第 56 章，接在增補 07（第 55 章）之後。v1.1 原檔與 `SHA256SUMS.txt` 不改。需求 ID 以 `GDP-`（Git 部署）與 `OBJ-`（物件儲存）開頭，驗收案例從 `T-252` 開始編號。
- **細化的既有需求**：CMP-002、CMP-008、CMP-009、GIT-008、GIT-018～020、DEP-009、BAK-001，以及增補 04（部署單元）、增補 06（網路模型）。

## 56.1 依據：實際 repo 的寫法

2026-11-08 讀了 HazelnutParadise 組織下 17 個有 `docker-compose.yml` 的 repo。共同寫法如下，每一種都會讓「把 compose 拉下來直接部署」出問題：

| 寫法 | 例子 | 直接部署會怎樣 |
|---|---|---|
| 共用外部網路 | infra-manager、super-minutes、llama-cpp-server 都寫 `networks: infra-net: external: true`；StoreCoach、whisper-api 用別名 `ollama-net: {external: true, name: infra-net}` | 目標主機沒有 `infra-net` 時，compose 直接失敗：「network infra-net declared as external, but could not be found」 |
| 跨專案用容器名稱呼叫 | super-minutes 寫 `WHISPER_GATEWAY_URL: http://whisper-gateway:5000`、`OLLAMA_URL: http://ollama:11434`，對方在別的 repo | 只要對方改名、搬主機或不在同一個網路，這個專案就壞，而且畫面上看不出兩個專案有關係 |
| 寫死 `container_name` | n8n-stack 的 `container_name: mysql`、whisper-api 的 `whisper-gateway` | 同一台主機不能同時跑 production 和 staging；也不能開多副本；增補 04 的無縫替換做不到 |
| 主機絕對路徑 | `/mnt/ssd1/n8n-stack/mysql:/var/lib/mysql`、`/mnt/hdd0/storecoach/db:/data/db` | 部署到另一台主機時，Docker 會自動建一個空目錄。資料庫看到空目錄會初始化成一個新的空資料庫，看起來部署成功，其實資料沒了 |
| 在主機上建置，映像用固定標籤 | infra-manager `image: infra-manager:latest` 加 `build:`；account-center `pull_policy: build` | 每次部署都覆蓋同一個 `latest`，舊映像變成沒有標籤的懸空映像，被清理後就無法回滾 |
| 機密寫在 compose 裡 | n8n-stack 的 `MYSQL_ROOT_PASSWORD=rootpassword`、`N8N_RUNNERS_AUTH_TOKEN=…`；jelly-cms 的 `DB_PASSWORD=jellypassword` | 機密跟著 repo 走，任何能讀 repo 的人都看得到 |
| Port 對所有位址開放 | `"5678:5678"`、`"1452:8080"`、`"5432:5432"` | 繞過反向代理和防火牆（Docker 直接寫 iptables），資料庫直接對外 |
| 必填變數 | `${DATA_DIR:?請設定 DATA_DIR}`、`${LOGTO_APP_ID:?必須設定 LOGTO_APP_ID}` | 增補 04 已處理：預檢擋下並列出缺哪些。本章補上：訊息照 repo 原文顯示 |
| 一個 repo 多個建置目錄 | surtopya 的 `./web` 與 `./api` 各有 Dockerfile | 只改 `web/` 也會重建 `api` |
| GPU | `gpus: all`、`deploy.resources.reservations.devices` | 目標主機沒有 NVIDIA Container Toolkit 時，容器建得出來但啟動失敗 |
| 浮動標籤 | `phpmyadmin/phpmyadmin:latest`、`ghcr.io/ggml-org/llama.cpp:server-cuda` | 不同主機、不同時間拉到不同版本，回滾也回不到同一份 |

本章的做法是：**不要求使用者改 repo**。平台在部署前讀懂這些寫法，能自動處理的在覆寫層處理，會出事的在預檢擋下或要求確認，並且把原因指到 compose 的行號。

## 56.2 既有 Compose 寫法的處理

**這些檢查怎麼做出來**（2026-11-14 使用者問能不能用 AI 偵測）：全部用固定規則，不用 AI。Compose 檔是結構化資料，外部網路、`container_name`、主機路徑、Port、建置、映像標籤都是讀欄位就知道，再向目標主機問一次現況（路徑在不在、網路在不在、Port 有沒有被佔用）。規則的結果每次相同、可以寫測試，不會把內容送到平台以外。只有兩項是推測，介面上要寫明依據並讓使用者否決：機密依變數名稱判斷（含 PASSWORD、SECRET、TOKEN、KEY 等），跨專案依賴依「共用網路上其他專案的服務名稱出現在變數值裡」判斷。

### 外部網路與跨專案呼叫

- **預檢**：列出 compose 裡所有 `external: true` 的網路，含別名（`ollama-net` → `infra-net`）。逐一檢查目標引擎環境有沒有這個網路。
- **網路不存在時**，提供三個選項，預設第一個：
  1. **建立這個網路**：平台建立同名網路，記進主機變更帳本（增補 07），標「平台安裝」。
  2. **對應到既有網路**：把 `infra-net` 對應到另一個已存在的網路。在覆寫層改，不動 repo。
  3. **改用平台的依賴連線**：依增補 06 的網路模型，把這個服務接到它依賴的元件專用網路。
- **共用外部網路的專案關係**：同一個引擎環境上，凡是加入同一個外部網路的部署單元，平台都畫進同一張拓撲，標「經由 infra-net」。環境變數裡出現另一個單元的容器名稱或服務別名時（例如 `http://whisper-gateway:5000`），平台把它記成依賴邊（增補 03 機制二），所以：
  - 改 whisper-api 的容器名稱、停止或刪除它時，影響預覽列出 super-minutes。
  - 把 super-minutes 搬到另一台主機時，預檢說明「whisper-gateway 在 hazel-tw-01，搬過去後連不到」，並提供改用內部位址（增補 04 的 `HZX_` 變數）。
- **不替使用者重寫**：平台不會自動把 `http://whisper-gateway:5000` 改掉，只標出依賴並提供改法。

### 寫死的 `container_name`

- **預檢**：同一個引擎環境已有同名容器（屬於別的單元或別的環境）時，擋下並指出 compose 行號，例如「compose 第 12 行 `container_name: mysql`，hazel-tw-01 上已有 n8n-stack production 的 mysql」。
- **提供的改法**：在覆寫層把名稱加上環境字尾（`mysql-staging`）。改名會讓靠容器名稱互相呼叫的其他專案連不到，所以只有在依賴圖上沒有外部引用者時才提供一鍵改名；有引用者時列出引用者，由使用者決定。
- 增補 04 的「無縫替換」判定照舊：寫死 `container_name` 就走「先停再起」。

### 主機絕對路徑（bind mount）

- **預檢**：列出所有 bind mount 的主機路徑，在目標主機上檢查：
  - 路徑存不存在。
  - 存在的話，是否在預期的磁碟上（對照增補 03 的裝置身分；`/mnt/ssd1` 應該是哪顆磁碟）。
  - 是否為空目錄。
- **路徑不存在，而且掛的是資料目錄**（資料庫、物件儲存、`/data`、`/var/lib/*` 這類，以及使用者標成資料的路徑）時：**擋下，不讓 Docker 自動建空目錄**。畫面寫出「這個路徑在 hazel-tw-01 上不存在。直接部署會建一個空目錄，postgres 會初始化成新的空資料庫」，並提供：
  - 選另一個已存在的路徑（資料夾選擇器）。
  - 從另一台主機搬資料過來（增補 06 的搬移流程）。
  - 明確確認「這是第一次部署，從空的開始」。
- **掛載點沒有掛上**：`/mnt/ssd1` 存在但磁碟沒掛上（目錄是根分割區上的空目錄）時，一律擋下。這是最常見的「資料寫到系統碟」來源。
- **`create_host_path: true`** 照 compose 語意處理，但同樣受上面的資料目錄規則限制。

### 在主機上建置的映像

- **標籤**：平台建置時，在覆寫層把映像標成 `hzx/<單元>/<服務>:<commit 前 12 碼>`，再另外加上 repo 寫的標籤（例如 `infra-manager:latest`）。這樣：
  - 每次部署的映像都留得住，回滾可以直接切回上一個 commit 的映像。
  - 映像清理預設保留每個服務最近 3 個部署版本（增補 03 依賴圖的「可回復版本」邊）。
- **建置位置**：在部署目標主機上建置（照使用者原本的習慣）。建置佔用的 CPU、記憶體在工作中心顯示，建置失敗不影響正在跑的版本。
- **只改部分目錄時**：一個 repo 有多個 `build.context` 時，平台比對這次 commit 改到的檔案，只重建 context 有變動的服務；沒變的服務沿用上一個映像。可以在單元設定裡關掉（每次全部重建）。

### 寫在 compose 裡的機密

- **偵測**：匯入與每次部署時，掃描 `environment` 裡名稱像機密（`*PASSWORD*`、`*SECRET*`、`*TOKEN*`、`*_KEY`）而且值是寫死字面值（不是 `${…}`）的項目。
- **處理**：不擋部署，在預檢顯示警告，並提供「移到平台變數」：平台在覆寫層把值換成變數組裡的機密參照，並提示使用者之後從 repo 刪掉、輪換這個值（因為它已經在 git 歷史裡）。
- 已經移到平台變數的，下次 repo 裡還有字面值時，以平台變數為準，並在預檢說明。

### 對所有位址開放的 Port

- **預檢**：列出所有 `ports` 裡沒寫主機位址（等於 `0.0.0.0`）的項目。資料庫類映像（postgres、mysql、mariadb、mongo、redis 等）的 Port 開到所有位址時，標成高風險，自動部署會暫停等批准（DEP-009）。
- **提供的改法**：在覆寫層改成 `127.0.0.1:<port>`，並建立 Zentinel 路由（網站服務）或留在內部（資料庫）。這是對外曝露頁「改綁 127.0.0.1」的同一個動作。
- 使用者也可以維持原樣，但記錄在部署紀錄裡。

### GPU 與浮動標籤

- **GPU**：compose 要求 GPU 時，預檢跑 AI-006 的四項 GPU 檢查。目標主機不通過時，擋下並說明缺什麼（驅動、Container Toolkit、裝置數量不足）。
- **浮動標籤**：`latest` 和沒有版本號的標籤（`server-cuda`）在部署時記下實際拉到的 digest，回滾回到同一個 digest。映像更新檢查（下一節）會比對 digest。

### 映像更新

- **檢查**：每天比對每個非建置服務的映像：
  - 有版本號的（`mysql:9.2.0`）：列出同一主版本的新版本（9.3.0）。
  - 浮動標籤的（`latest`）：比對遠端 digest 有沒有變。
- **呈現**：專案頁和容器頁標「有新版映像」，點開看新舊版本與 Release 連結。更新是一次普通部署：在覆寫層改版本號，走預檢、批准與回滾。
- **不自動更新**：預設只通知。使用者可以對單一服務開「自動套用小版本更新」，仍走預檢與批准規則。

## 56.3 分支觸發部署

規格 15.8 與 CMP-009、GIT-018～020 已經定義 Webhook、定期檢查、簽章驗證與去重。本節補上畫面與行為細節。

- **以環境為單位綁定分支**：每個環境選一個觸發來源，例如 production 聽 `main`、staging 聽 `develop`。觸發來源有三種：
  - **分支**：指定分支名稱。
  - **分支樣式**：例如 `release/*`。同一時間只能對應到一個環境，兩個環境的樣式重疊時，設定時就擋下。
  - **標籤樣式**：例如 `v*`，用在「只有打版本標籤才上正式環境」。
  - **樣式的寫法**（分支、標籤共用，和路徑篩選同一套）：`*` 是任意文字但不跨過 `/`，`**` 可以跨過 `/`，`?` 是剛好一個字，`!` 開頭是排除，一行一條、符合任何一條就算。不支援正規表示式。介面上叫「符合規則的分支／標籤」，寫法要直接列在輸入框旁邊，並即時顯示目前符合哪些分支或標籤、被排除哪些。
- **觸發方式**：Webhook（GitHub 送事件，幾秒內開始）或定期檢查（預設每 5 分鐘，可改 1～60 分鐘）。主機或管理入口沒有對外網址時，只能用定期檢查，畫面說明原因。兩者都開時，先到的觸發部署，另一個合併成同一個要求（規格 1562 行）。
- **路徑篩選**：可以設定「只有改到這些路徑才部署」，例如 `web/**`；以及「改到這些路徑不部署」，例如 `docs/**`、`*.md`。只改了被排除的路徑時，部署紀錄記一筆「略過：只改了 docs/」。
- **略過標記**：commit 訊息含 `[skip deploy]` 或 `[skip ci]` 時不部署，記一筆略過。
- **連續推送**：同一個環境在部署進行中又收到新的 push 時，排隊的舊要求直接作廢，只保留最新的 commit。正在跑的部署不中斷，跑完再接最新的。部署紀錄標「已被 a1b2c3d 取代」。
- **批准照舊**：自動部署遇到高風險變更（DEP-009、本章的 Port 與資料目錄規則）時暫停等批准；批准畫面寫「由 push 觸發：tim 推到 main」。
- **回寫 GitHub**（選用，需要額外權限，GIT-014）：在 commit 上寫部署狀態（GitHub Deployments 或 commit status），包含環境名稱、結果和平台的部署紀錄連結。沒有權限時這個選項顯示停用與原因。
- **暫停自動部署**：每個環境有一個開關，關掉後 push 仍會記錄（「收到 a1b2c3d，自動部署已暫停」），之後可以手動部署那個 commit。
- **觸發結果只分五種**：已部署、部署中、等批准、失敗、略過。取代、路徑篩選、略過標記、暫停自動部署都算「略過」，原因用滑過或聚焦顯示，例如「已被 9b3e7f1 取代」「只改了 README.md」。
- **分支被刪除或強制推送**：照 GIT-020，分支刪除不刪應用，只停止觸發並標示；強制推送使目前部署的 commit 不在分支上時，標「目前版本已不在 main 的歷史中」，不自動回滾。

## 56.4 物件儲存

### 選哪一套

MinIO 社群版已經不能用：2025 年 10 月起不再發布映像與執行檔，2025 年 12 月進入維護模式，主 repo 在 2026 年 4 月封存，Docker Hub 上的映像在 2026 年 9 月也拉不到了。

| 選項 | 授權 | 狀態（2026-11-08 查證） | 適合 |
|---|---|---|---|
| **RustFS** | Apache 2.0 | 2026-09-16 發布 1.0.0，目前 1.0.4（2026-10-25）。單機與分散式、IAM 與政策、生命週期、Bucket 複寫、配額、事件通知、Web 主控台都標「Available」；讀取 MinIO 既有資料目錄標「Preview」 | **預設**。單機到中型、需要主控台與 MinIO 相同的使用方式 |
| SeaweedFS | Apache 2.0 | 4.52（2026-11-02），最久經使用的替代品 | 大量小檔案、多台主機的大容量 |
| Garage | AGPL-3.0 | 持續開發，S3 功能較少（沒有 bucket policy、ACL、版本控制） | 低資源、多地點的小叢集 |
| pgsty/silo | AGPL-3.0 | MinIO 社群版的分支，持續發布映像 | 只用來接手既有 MinIO 部署 |

- **預設用 RustFS**：授權沒有 AGPL 的限制、單機就能跑、有主控台、S3 功能最接近 MinIO。
- **風險**：RustFS 的 1.0 才發布不到兩個月。所以平台不把物件儲存綁死在 RustFS 上：引擎以轉接層實作（和服務模組的 adapter 同一套做法），第一版做 RustFS，SeaweedFS 列為第二個引擎。使用者看到的是「物件儲存」，不是某一套軟體。
- **版本**：平台固定引擎映像版本，升級走一般的部署流程（預檢、備份、可回滾）。

### 使用者可以做什麼

物件儲存放在側欄「資料」群組，跟資料庫並列。

- **建立物件儲存服務**：選主機、選磁碟與資料目錄（資料夾選擇器，預設位置規則同模型庫）、選引擎。以平台管理的容器執行，在專用網路 `hzx-objstore-<名稱>` 上（增補 06）。S3 端點只綁 127.0.0.1；要給外部用時，經 Zentinel 開網域，並自動申請憑證。
- **Bucket**：建立、刪除（非空 bucket 刪除前列出物件數與大小，要輸入名稱確認）、設定公開讀取或私有、配額、版本控制（引擎支援時）、生命週期規則（例如 30 天後刪除 `tmp/` 底下的物件）。
- **存取金鑰**：每個金鑰指定可用的 bucket 與權限（唯讀、讀寫）。金鑰的 Secret 只在建立時顯示一次，之後存在機密庫。可以停用、輪換、設定到期日。
- **給應用用**：部署單元宣告依賴某個 bucket 時，平台建立一把只能用這個 bucket 的金鑰，並注入 `HZX_S3_ENDPOINT`、`HZX_S3_BUCKET`、`HZX_S3_ACCESS_KEY_ID`、`HZX_S3_SECRET_ACCESS_KEY`，把應用接到物件儲存的專用網路。依賴邊進影響預覽。
- **瀏覽物件**：資料夾式瀏覽、上傳、下載、刪除、產生有效期限的分享連結（預設 1 小時，最長 7 天）。大量物件時用分頁與前綴搜尋，遵守增補 03 機制六的列表上限。
- **當備份目的地**：BAK-001 的「S3 相容」目的地可以直接選平台的 bucket，不必另外填端點與金鑰。備份到同一台主機的 bucket 時，警告「備份和原始資料在同一台主機」。
- **用量**：每個 bucket 的物件數、大小、最近 24 小時的請求數與流量。
- **接管既有 MinIO**：偵測到主機上的 MinIO 容器時，標「控制者：外部」唯讀觀察（44.2）。提供遷移到 RustFS：建新服務、逐個 bucket 複製並比對物件數與大小、切換應用的端點、保留舊服務 7 天。

## 56.5 需求

| ID | 使用者需求 | 完成條件 |
|---|---|---|
| GDP-001 | 部署前，平台列出 compose 用到的外部網路，目標環境沒有時提供建立、對應或改用依賴連線。 | 含別名（`name:`）；建立的網路寫進主機變更帳本；不動 repo。 |
| GDP-002 | 平台把共用外部網路與環境變數裡的跨專案容器名稱記成依賴。 | 停止、改名、刪除或搬移被依賴的單元時，影響預覽列出依賴者；搬主機時預檢說明連不到並提供內部位址。 |
| GDP-003 | 寫死的 `container_name` 與同環境既有容器衝突時，部署前擋下並指出行號。 | 沒有外部引用者時提供一鍵加環境字尾；有引用者時列出引用者。 |
| GDP-004 | 資料目錄的 bind mount 路徑不存在或掛載點沒掛上時，部署前擋下，不讓 Docker 建空目錄。 | 提供選既有路徑、搬資料、或明確確認從空的開始；掛載點未掛上一律擋下。 |
| GDP-005 | 平台建置的映像都帶 commit 標籤，回滾可以切回上一個 commit 的映像。 | 同時保留 repo 寫的標籤；清理預設保留每個服務最近 3 個部署版本。 |
| GDP-006 | 一個 repo 有多個建置目錄時，只重建這次有改動的服務。 | 比對 commit 改到的檔案與 `build.context`；可以關掉。 |
| GDP-007 | 平台偵測 compose 裡寫死的機密，並提供移到平台變數。 | 不擋部署；移動後在覆寫層改用機密參照；提示從 repo 刪除並輪換。 |
| GDP-008 | 資料庫類映像的 Port 開到所有位址時，標高風險並提供改綁 127.0.0.1。 | 自動部署暫停等批准；改法在覆寫層；維持原樣時記入部署紀錄。 |
| GDP-009 | 浮動標籤的映像記下實際 digest，回滾回到同一個 digest。 | 部署紀錄顯示 digest。 |
| GDP-010 | 平台每天檢查映像新版並通知，不自動更新。 | 版本號比對同主版本新版、浮動標籤比對 digest；更新是一次普通部署；可對單一服務開自動套用小版本。 |
| GDP-011 | 每個環境可以綁定分支、分支樣式或標籤樣式作為觸發來源。 | 兩個環境的樣式重疊時設定時擋下；支援 Webhook 與定期檢查（1～60 分鐘）。 |
| GDP-012 | 可以設定路徑篩選與略過標記。 | 只改排除路徑或 commit 含 `[skip deploy]`／`[skip ci]` 時記一筆略過，不部署。 |
| GDP-013 | 部署進行中又收到 push 時，只保留最新的 commit。 | 排隊的舊要求作廢並標「已被 … 取代」；正在跑的部署不中斷。 |
| GDP-014 | 每個環境可以暫停自動部署，並可選擇回寫部署狀態到 GitHub。 | 暫停時 push 仍記錄；回寫需要額外權限，沒有權限時顯示停用與原因。 |
| OBJ-001 | 管理員可以在指定主機與磁碟建立物件儲存服務。 | 以平台管理的容器執行，固定版本；專用網路；端點只綁 127.0.0.1，對外經 Zentinel。 |
| OBJ-002 | 物件儲存以轉接層實作，第一個引擎是 RustFS。 | 畫面與 API 不出現引擎專屬的概念；換引擎不改應用拿到的變數。 |
| OBJ-003 | 管理員可以管理 bucket：公開或私有、配額、版本控制、生命週期。 | 引擎不支援的功能顯示停用與原因；非空 bucket 刪除前列出物件數與大小並要求輸入名稱。 |
| OBJ-004 | 管理員可以建立限定 bucket 與權限的存取金鑰。 | Secret 只顯示一次並存進機密庫；可以停用、輪換、設定到期日。 |
| OBJ-005 | 部署單元可以宣告依賴 bucket，平台自動發金鑰並注入變數。 | 金鑰只能用該 bucket；依賴邊進影響預覽。 |
| OBJ-006 | 使用者可以瀏覽、上傳、下載、刪除物件，並產生有期限的分享連結。 | 分頁與前綴搜尋；分享連結預設 1 小時、最長 7 天。 |
| OBJ-007 | 備份目的地可以直接選平台的 bucket。 | 備份到同主機的 bucket 時警告。 |
| OBJ-008 | 主機上的既有 MinIO 唯讀接管，並可遷移到平台的物件儲存。 | 逐 bucket 複製並比對物件數與大小；切換端點；舊服務保留 7 天。 |

## 56.6 驗收案例

| ID | 情境 | 預期結果 |
|---|---|---|
| T-252 | 匯入 super-minutes 到 hazel-jp-02，那台沒有 `infra-net`。 | 預檢列出 `infra-net`（external），提供建立、對應、改用依賴連線三個選項；選建立後，主機變更帳本多一筆「平台安裝：network infra-net」。 |
| T-253 | 停止 whisper-api，super-minutes 的變數裡有 `http://whisper-gateway:5000`。 | 影響預覽列出 super-minutes，原因是「環境變數 WHISPER_GATEWAY_URL 指向 whisper-gateway」。 |
| T-254 | 在 hazel-tw-01 部署 n8n-stack 的 staging 環境，production 已經在跑。 | 預檢擋下，指出 compose 第 N 行 `container_name: mysql` 與 production 衝突；沒有外部引用者，提供一鍵改成 `mysql-staging`。 |
| T-255 | 部署 StoreCoach 到新主機，`/mnt/hdd0/storecoach/db` 不存在。 | 擋下並說明 mongo 會初始化成空資料庫；提供選既有路徑、搬資料、確認從空的開始。 |
| T-256 | `/mnt/ssd1` 目錄存在但磁碟沒掛上。 | 擋下，說明「/mnt/ssd1 在根分割區上，不是預期的磁碟」。 |
| T-257 | infra-manager 連續部署兩個 commit 後，回滾到前一個。 | 不重新建置，直接用 `hzx/infra-manager/app:<前一個 commit>` 啟動。 |
| T-258 | surtopya 的 commit 只改了 `web/`。 | 只重建 web；api 沿用上一個映像，部署紀錄寫「api：沿用，context 沒有變動」。 |
| T-259 | 匯入 n8n-stack。 | 預檢警告 `MYSQL_ROOT_PASSWORD` 等 4 個寫死的機密；選「移到平台變數」後，覆寫層改用機密參照，原值不出現在部署紀錄。 |
| T-260 | jelly-cms 的 postgres 沒有寫 Port；改成 `"5432:5432"` 後 push 到 main。 | 自動部署暫停等批准，原因是「postgres 的 5432 開到所有位址」；提供改綁 127.0.0.1。 |
| T-261 | production 聽 `main`、staging 聽 `release/*`，新增第三個環境聽 `release/v2`。 | 設定時擋下：`release/v2` 符合 staging 的 `release/*`。 |
| T-262 | 在 surtopya 設定「只有改到 `web/**` 才部署 web 單元」，push 一個只改 `README.md` 的 commit。 | 不部署，部署紀錄記一筆「略過：只改了 README.md」。 |
| T-263 | production 部署進行中，連續 push 了 b 與 c 兩個 commit。 | b 的要求標「已被 c 取代」；目前的部署跑完後部署 c；總共只有兩次部署。 |
| T-264 | 暫停 production 的自動部署後 push。 | 不部署；部署紀錄記「收到 d，自動部署已暫停」；可以從那筆記錄手動部署 d。 |
| T-265 | 在 hazel-tw-01 的 /mnt/ssd1 建立物件儲存 `media`，建 bucket `uploads` 與只能讀寫 `uploads` 的金鑰。 | 服務在 `hzx-objstore-media` 網路；端點綁 127.0.0.1；金鑰 Secret 只顯示一次；用這把金鑰存取別的 bucket 被拒絕。 |
| T-266 | shop 的 web 單元宣告依賴 `uploads`。 | 部署後容器拿到四個 `HZX_S3_*` 變數；web 接上 `hzx-objstore-media`；停止 media 的影響預覽列出 shop web。 |
| T-267 | 主機上有一個 MinIO 容器，裡面有 2 個 bucket，選遷移。 | MinIO 標「控制者：外部」；遷移後兩邊的物件數與大小一致，應用改用新端點，MinIO 保留 7 天後才可刪除。 |
