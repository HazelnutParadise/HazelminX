# 0032 — Agent 壓縮已結束的步驟紀錄，被壓縮的步驟仍留下結果

**Status:** accepted
**Date:** 2026-11-12

## Context
決策 0029 讓 Agent 在每個步驟前後先寫 `journal.jsonl` 再回報，但檔案只增不減，`Journal` 也把每筆紀錄留在記憶體，節點跑幾個月就會無限成長（票 122）。

壓縮時有一個限制：Core 收到事件就先回 `ack`，之後才存工作狀態（`core/internal/nodes/session.go` 處理 `event` 的分支）。Core 若在兩者之間當掉，重啟後會用 `step_reconcile` 問這一步。Agent 如果因為紀錄已被壓縮而回「沒開始過」，Core 會重跑這一步（`core/internal/jobs/engine.go` 的 `Reconcile`）。所以「Core 確認過」不等於「Core 已經存下結果」。Agent 也看不到 Core 的工作狀態，協定沒有這個欄位。

## Decision
保留 0029 的內容：每個步驟開始前與結束後先寫 `journal.jsonl` 並 fsync 才回報；同一工作步驟有完成或失敗紀錄就不重跑；中斷的步驟只有 Core 對帳後送來、而且標記可重試時才再跑。

另外加上壓縮：

- 一個工作的每筆紀錄都被確認、每個步驟最後一筆都是 completed 或 failed，才算已結束。已結束的工作整批移出，不會只移一部分。
- 已結束的工作在最後一筆滿 7 天後移出。比它新的已結束紀錄超過 1 萬筆時，也會提早移出。
- 移出的紀錄完整寫進 `journal.archive.jsonl`。這個檔只做稽核用，到 16 MiB 就換一代，只留前一代。
- 每個被移出的步驟，把最後一筆紀錄（不含 `result`）留在 `journal.outcomes.jsonl`，最多留 5 萬個步驟。對帳照這份結果回報。失敗的步驟照樣重送失敗事件。完成的步驟再收到 `step_execute` 時回 `OUTCOME_UNKNOWN`，讓 Core 先對帳。已結束的步驟不能再開始。
- 三個檔都先寫暫存檔或追加後 fsync，再改名並 fsync 目錄。順序是封存檔、結果檔、`journal.jsonl`，任何一步斷電都只會留下舊版或新版。

## Options rejected
- 只看「已確認」就把步驟忘掉：Core 在確認與存檔之間當掉時，會重跑已完成的步驟，連不可逆的步驟也一樣。
- 從封存檔查被壓縮的步驟：每個新步驟都要掃一次磁碟上最多 32 MiB 的檔案，或在記憶體裡替封存檔建索引，代價比只留結果高。
- 讓 Core 存檔後才回 `ack`，或讓協定告訴 Agent 工作已結束：這樣最乾淨，但要改 Core 和訊息契約，不在票 122 的範圍。

## Consequences
- 影響的票：007、008、122。
- 被壓縮的步驟超過 5 萬個後，最舊的結果會刪掉，這些步驟會再被當成沒開始過。要出事必須同時發生兩件事：Core 在確認後、存檔前當掉，而且這個工作在之後至少 5 萬個步驟結束的期間都沒對帳成功。根治要改 Core 的確認時機。
- 舊版 Agent 讀不懂壓縮後 `journal.jsonl` 的第一行，降版後開檔會失敗，但不會遺失資料。
