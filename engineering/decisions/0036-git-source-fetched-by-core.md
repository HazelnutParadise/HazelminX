# 0036 — Git 來源由 Core 在記憶體裡抓取固定 commit，抓到的檔案變成一般的單元內容

**狀態：** 已採用（票 049.1，2026-11-14）

## 背景

票 049 讓 Compose 單元的來源可以是 Git repo。要決定在哪裡抓：Core，或節點經高權限執行器。限制有這些：

- 抓取要憑證：GitHub App 的安裝 token 由 Core 用 App 私鑰簽出（047.1），PAT 與 SSH Deploy Key 存在 Core 的機密庫。GIT-025 要求 App 私鑰不出 Core，抓取憑證不進 Git URL、全域設定、映像、日誌或一般建置環境。
- repo 的內容不可信。原生 `git clone` 會依 repo 內容做事：checkout 時跑 LFS 等 filter、跟著 submodule 去抓別的位址、寫出可以指到目錄外的符號連結；hook 與 `.git/config` 雖然不隨 clone 下載，但工作目錄一旦被其他工具當成 repo 打開，就可能被執行。這週的審查教訓是：以 root 執行的程式不能接受呼叫端給的路徑或指令，抓下來的內容不能碰到抓取目錄以外的東西，也不能在建置以外的地方於主機上執行程式。
- 044.1 只從內容解析 Compose（0034），044.2 以內容定址的方式把檔案送到節點、授權憑證綁定內容摘要（0035）。這兩段已經審過，不該再開第二條路。

## 決定

1. **Core 抓取，不在磁碟上，不呼叫 `git` 程式。** Core 用純 Go 的 Git 客戶端（go-git v5）把一個 commit 抓進記憶體：只要求那一個 SHA、深度 1、不抓 tag。不做 checkout，所以沒有 filter、hook、`.git/config`、工作目錄或符號連結會被解讀；Core 只把 Git 物件當資料讀。submodule 只以樹裡的 gitlink 被看見，不跟著去抓。
2. **ref 由 Core 先固定成 commit。** GitHub 連線用 048.1 的 `ResolveRef`；手動 URL 用 Git 協定列出遠端 ref。部署綁定存的是 SHA，抓取只要那個 SHA，抓到的 commit 物件雜湊不等於 SHA 就拒絕。之後分支移動不影響已經存下的內容。
3. **抓到的檔案變成一般單元內容。** 從樹裡取出主檔、合併檔，以及 Compose 以相對路徑引用、而且在樹裡存在的檔案（bind mount 來源、`env_file`、檔案型的 secrets 與 configs）。這些檔案以 044.1 的同一套限制（數量、大小、UTF-8）存成單元的新版本，之後的驗證、預覽、change plan、批准、主機預檢與部署全部照 044.1、044.2 原樣進行。節點收到的只有檔案內容，從來沒有憑證。
4. **擋下 049.1 還不支援的東西。** 要用的檔案是符號連結、gitlink（submodule）或 Git LFS 指標檔，或任何服務有本機 `build:` 時，Core 拒絕並寫出原因，不部署缺檔的內容。049.2 補上建置、submodule 與 LFS。
5. **憑證只在 Core 的這一次請求裡。** HTTPS 的 token 只放在請求的驗證標頭；SSH 金鑰只在 SSH 驗證裡用。URL 不得帶使用者資訊。錯誤訊息與日誌先把憑證值換掉才回傳。不跟隨任何 HTTP 轉址。
6. **連線前檢查位址。** 手動 URL 只收 `https://` 與 `ssh://`（或 `user@host:path`）。實際連線時才檢查解析出的位址：迴路、鏈路本地（含雲端中繼資料 169.254.169.254）、未指定與多播位址一律拒絕；SSH 先解析再以位址連線，避免解析結果在檢查後被換掉。測試用的本機 Git 伺服器透過 Core 的建構選項開放，正式設定不能開。
7. **SSH 主機金鑰必須事先固定。** 手動 SSH 來源要提供主機公鑰，Core 只接受這一把，不讀 `known_hosts`，不接受第一次連線就信任。
8. **抓取有上限。** 一次抓取有時間上限，SSH 的連線與交握也算在內（go-git 交握時不看呼叫端的期限，所以由 Core 自己的撥號程式把期限放在連線上）。記憶體以「宣告大小」擋：Core 先收原始 pack（有上限），解析前逐一讀物件標頭的宣告大小與 delta 展開後的大小，超過上限就拒絕，不先解壓到記憶體。每個 HTTP 回應本身也有上限。連線失敗與憑證被拒只回固定的原因，不回伺服器或網路的原文，免得被拿來分辨內網哪個 Port 有開。Core 主機的 `~/.ssh/config` 不會被讀。
9. **部署綁定來源。** 單元的 Git 綁定（連線參照或 URL、Repo ID、來源站台、ref、SHA、取出的路徑）有自己的摘要，寫進單元版本與 change plan 內容；部署紀錄記下 SHA。產生計畫與部署工作開始前都再檢查一次：GitHub 連線仍可用、仍涵蓋這個 Repo ID；手動 URL 的單元以存下的憑證列一次遠端 ref，確認憑證沒被撤銷；單元版本也還是計畫批准的那一版。任何一項不成立就拒絕。

## 不採用的做法

- **在節點上抓。** 要把 token 或 SSH 金鑰送到節點；安裝 token 雖然短命，PAT 與 Deploy Key 是長期的。執行器還得以 root 跑 Git，處理 repo 內容可能帶來的符號連結、submodule 與 filter，這正是這週審查要它避免的事。節點能直接連 GitHub 也不是每台主機都有的前提。唯一的好處是大型 build context 不必經 Core 轉送，這留給 049.2 處理分段傳送時再看。
- **Core 呼叫 `git` 程式抓到暫存目錄。** 會讀 Core 主機的全域與系統 Git 設定、credential helper 與環境變數；checkout 會跑 filter、寫符號連結；憑證要經命令列、環境或 helper 傳給子行程。要把這些全部關掉的旗標很多，漏一個就出事。
- **只用 GitHub 的 tarball API。** 只適用 GitHub 連線，手動 URL 與 SSH 還是要 Git 協定；兩條抓取路徑反而多一份要審的東西。

## 後果

- Core 多了 go-git 依賴（Apache-2.0）。升級時要重看它是否新增會讀磁碟或全域設定的路徑。
- 匯入或換 commit 是一次同步的 API 呼叫，受時間與大小上限保護；單元內容的上限（768 KiB）也限制了 Git 來源能取出的檔案。需要大量檔案的 build context 由 049.2 另行設計。
- 安裝 token 從不寫進資料庫；PAT 與 SSH 金鑰存在機密庫，consumer 綁定單元。
- 影響的票：049.2（建置與 submodule／LFS 沿用「Core 抓、節點只收內容」）、050（自動部署只是用新 SHA 再跑一次同一條路）、051（連線共用與輪替）。
