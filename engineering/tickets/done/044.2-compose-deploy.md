## What it delivers

部署是一個工作：Core 把 044.1 驗證過的單元內容（檔案、主檔與合併順序、profiles、固定的 Compose 專案名稱、目標引擎環境）簽進授權憑證，Agent 轉給高權限執行器的固定動作。執行器自己決定主機上的目錄（平台擁有的 `/var/lib/hazelminx/compose/<Compose 專案>/`），把檔案寫進每次部署各自的來源目錄，以乾淨的環境、`-p`、`-f`、`--profile` 執行原生 `docker compose`（Podman 環境用 Docker Compose CLI 連它的 socket），不接受呼叫端給的路徑或指令。每個變更寫進主機變更帳本，並定義移除方式。

- 需要主機的預檢：映像取得、磁碟空間、主機 Port 衝突、bind mount 來源存在。
- 含高權限設定（044.1 預覽列出的 privileged、主機網路、掛引擎 socket 等）的部署走 change plan，批准綁定內容摘要。
- 建置來源與持久資料分開：來源目錄每次部署各一份，持久資料放命名儲存卷或平台的資料目錄，切換版本不讓運行中的服務失去設定檔。
- 列出以節點為目標的單元，補票 019 的 NOD-008。

## Acceptance criteria

- [x] **CMP-007** 管理員可以先驗證完整部署設定。 — 完成條件：缺必要變數、無法取得映像、相對路徑錯誤、磁碟缺席、Port 衝突都在修改前顯示。（缺變數與相對路徑在 044.1 完成） — 已完成：主機預檢是部署工作的第一步，也可以用 `POST …/compose/host-checks` 單獨跑（唯讀工作 `compose.check`）。執行器以原生 `docker compose config` 的結果檢查：映像在主機或 registry 找不到（`IMAGE_UNAVAILABLE`）、磁碟剩餘不到 1 GiB（`DISK_LOW`，5 GiB 以下警告）、主機 Port 已被占用（`PORT_IN_USE`）、bind mount 來源不存在（`BIND_SOURCE_MISSING`）、同名 Compose 專案不是平台部署的、沒有引擎或引擎沒回應。部署步驟動手前再查一次，有錯就不改主機、不留修訂版目錄。證據：真引擎互通 `TestInteropDeploysThroughTheRealAgentExecutorAndDocker` 的第 1、6、9 段；`TestComposeHostCheckFailureChangesNothing`。registry 不回應時只記警告（`IMAGE_UNCHECKED`），不擋部署。

## Notes

### 交付紀錄（2026-11-14，PR #183）

- **T-052（部署部分）**：互通測試以原生 Compose 部署多檔、profiles、build 與相對路徑，結果就是原生 Compose 的結果（執行器不自己解析）。
- **測試環境**：macOS 上 `go test -race ./...`；Linux 容器（hzx-ledger-test:trixie）以 root 與 uid 65534 各跑 `cargo test --workspace`；真引擎互通在特權容器內的 dockerd 26.1.5、Compose 2.26.1，Agent 以 uid 65534、執行器以 root。CI 新增同一個互通步驟（GitHub runner 的 Docker）。
- **獨立審查發現並已修正**：執行器的 Compose 原本會讀 `.env`、`HOME` 與 `~`，Core 分析時沒有，`/etc`、`/root` 的掛載可以不經擁有者批准部署（P1）。現在以 `--env-file /dev/null`、不給 `HOME` 執行，執行器再以 044.1 的高風險規則檢查原生結果，清單沒標明擁有者批准就拒絕；044.1 把 `~` 視為 `/root`。其他修正：資料目錄改為 `data/` 底下一層並拒絕巢狀資料路徑（容器換連結的 TOCTOU）、帳本加入儲存卷與網路和移除方式、部署結果與證據也遮罩機密、斷線後經對帳完成的部署會結束部署紀錄、部署歷史把工作已結束但紀錄仍是 running 的列標成 failed。
