# 039.1 — Agent 與 Core 偵測並提供每個節點的 Docker、Podman、K3s 狀態與環境

**Epic:** 容器引擎（`epic:containers`）  
**User Story:** 管理員可以管理容器引擎  
**Milestone:** M2 容器、Compose 與 GitHub  
**Parent:** 039  
**Blocked by:** 019 管理員可以用一次性註冊碼加入節點，並看到離線、過期、維護與撤銷狀態, 012 維運者可以執行需要高權限的固定動作，而 Agent 主程序維持低權限

## What it delivers

高權限執行器的唯讀動作 `engine_inspect`（權限 `host.engines.read`）以 root 讀取 Docker、Podman、K3s 的程式、版本、systemd 單元、Docker CLI 外掛（compose、buildx），以及每個引擎 socket 對 `GET /version`、`GET /info` 的回答。Agent 收到 Core 的 `engines_probe`（能力 `host.engines` v1）就把授權憑證轉給執行器，報告原樣轉回。Core 在節點連上時、連線期間每 5 分鐘、以及 `POST /management/v1/nodes/{id}/engines/refresh` 時詢問，只保存最新一份報告與最新一次失敗（migration 0013），以 `GET /management/v1/nodes/{id}/engines` 提供。通道訊息寫在 `engineering/contracts/README.md`「容器引擎」。安裝在 039.2，畫面在 039.3。

## Acceptance criteria

- [ ] **NOD-003**（後端）管理員可以看到各引擎的安裝、執行、版本與可管理能力。 — 完成條件：分開顯示 Docker、Podman、Kubernetes／K3s、Swarm 與相關 runtime，不重複計數同一工作負載。
- [ ] **NOD-004**（後端）管理員可以管理不同 Linux 使用者的 rootless Podman 環境。 — 完成條件：明示擁有者與 socket；甲使用者容器不誤顯示為乙使用者資源。
- [ ] **ENV-001**（後端）每個節點列出所有環境（引擎＋擁有者＋連接端點），同種引擎多個時各自一列。
- [ ] **ENV-002** 以端點實際回應的引擎判斷種類（`podman-docker` 的 docker.sock 辨識為 Podman）。
- [ ] 狀態分開：未安裝、已停止、不相容、無權限、無回應、讀不到 systemd 各自一種狀態，不把全部問題當成沒安裝（INS-008 的狀態部分；INS-008 由 039.2 擁有）。
- [ ] 讀不到的值是 `null`，看不到的範圍列在 `uninspected`，不猜。
- [ ] 使用者的 `/run/user/<uid>/` 路徑連到別處或不屬於該使用者時，執行器不連線。

## Acceptance tests（第 42 章與增補 02）

- **T-051** 同主機有 Docker、rootful 與兩個 rootless Podman。 → 分開辨識四個環境與使用者，不混淆容器。
- **T-149** 同一台有 rootful Docker 與 tim 的 rootless Docker。 → 辨識為兩個 Docker 環境，擁有者與 socket 分開。
- **T-150** 裝了 `podman-docker`，`/var/run/docker.sock` 指向 Podman。 → 辨識為 Podman 環境，不顯示成 Docker。
- **T-156** 一個 Docker 環境的 socket 消失（服務停了）。 → 只有該環境標為無法連線，同節點其他環境照常。
