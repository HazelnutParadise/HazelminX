# 020.4 — 維運者可以在主機頁看到主機資訊、硬體卡片與趨勢圖，耗盡狀態會被標出

**Epic:** 主機管理（`epic:host`）  
**User Story:** 維運者可以掌握主機狀態  
**Milestone:** M1 單機主機管理  
**Parent:** 020  
**Blocked by:** 020.1 Agent 回報主機資訊與資源指標，Core 保存有解析度的歷史並以 API 提供, 017 使用者可以在主導覽、全域搜尋與工作中心之間完成日常操作  
**規格章節:** 07｜介面與操作體驗、29｜監控、GPU、事件與告警  
**Issue:** [#158](https://github.com/HazelnutParadise/hazelminx/issues/158)  

## What it delivers

主機頁與總覽頁的畫面（畫板 `design/screens/NodeDetail.dc.html`、`Overview.dc.html`），資料來自 020.1 的 API；以及需要建檔或寫入的工作在預檢時擋下 inode 用盡或唯讀的檔案系統。

## Acceptance criteria

證據路徑以 `web/` 為準。單元測試以 `vp test` 執行；e2e 以 `playwright test` 對這個分支建置的 Core 執行（`e2e/start-core.sh`），另外設 `HAZELMINX_E2E_AGENT_BIN`（Linux 版 `hazelminx-agent`）與 `HAZELMINX_E2E_AGENT_ADDR=0.0.0.0:19891` 時，`e2e/host-monitoring.spec.ts` 會在容器裡跑真的 Agent：用畫面上的碼註冊、連線、回報主機資訊與指標。2026-11-14，macOS arm64，OrbStack 容器（Debian 13，aarch64）。

主機頁（`/nodes/{id}`）的「概況」分頁由這張票提供（`src/nodes/monitor/`）；票 125 的身分、連線、憑證、維護面板移到「系統」分頁（`/nodes/{id}/system`）。主機清單每一列連到「概況」。

- [ ] **MON-005**（畫面）即時與歷史趨勢圖保留缺口、標示解析度，不補零。 — 主機頁部分已完成：六個時間範圍（即時 5 分、1 小時用原始點，12 小時、24 小時、7 天、30 天用 5 分鐘彙總），範圍列旁寫「每點 10 秒」或「每點 5 分鐘平均」；`gapBefore` 的點另起一段線，沒有資料的區間寫「這段時間沒有資料」，不畫平線；資料過期時最後一點畫空心圓。證據：`src/nodes/monitor/overview.test.tsx`「draws a gap as a break in the line…」（拿掉斷線邏輯後這條會失敗，已實測）「reads one hour of raw points by default and 5-minute points for 7 days」「says a period has no data…」；e2e「a host that never reported…」（即時、12 小時、30 天都送出 Core 接受的區間，回 200）與真 Agent 流程（即時範圍畫出線、表格檢視列出各點）。未完成：總覽頁（畫板 Overview）的趨勢圖還沒做。
- [x] 主機資訊（OS、核心、架構、開機時間、時區、時間同步）顯示來源與更新時間，未知欄位顯示「未提供」。 — 證據：`overview.test.tsx`「shows each fact with where it was read from, and 「未提供」…」「says the host has not reported yet…」；真 Agent：每一欄下面有來源（`/etc/os-release`、`/proc/sys/kernel/osrelease`、`uname`、`/proc/stat btime`、`/etc/localtime`、`adjtimex`），面板標題旁有「收集於」。
- [ ] 節點硬體依類別分組成卡片（CPU、記憶體、磁碟、GPU、網卡、溫度），一組超過 4 個改依使用率排序的精簡橫條並收合其餘；溫度列出所有讀得到的感測器（hwmon、smartctl／nvme、NVML、IPMI），以各自臨界溫度畫比例並標來源（畫板 NodeDetail「硬體」）。 — 已完成：CPU（各核依使用率排序、超過 4 個收進「全部 N 個」）、記憶體與 Swap、系統上限（程序數、檔案控制代碼、記憶體壓力）、檔案系統、網卡（有連線速度時以速度為滿格）、溫度（以各自臨界溫度畫比例、標晶片與來源、依「目前／臨界」排序）。證據：`overview.test.tsx`「lists the four busiest cores…」「orders temperature sensors…」「leaves the loopback interface out…」。未完成：GPU 卡片（票 020.2 的資料）；溫度只有 Agent 目前回報的 hwmon 與 thermal zone，smartctl／nvme、NVML、IPMI 來源要等 020.3、020.2。
- [ ] 需要建檔或寫入的工作，預檢時擋下 inode 用盡或唯讀的檔案系統並寫出原因（增補 03 51.3「預檢」）。 — 未做：這是工作引擎的預檢，不在 `web/`。畫面這一側已經把 inode 用盡標出來（見 T-165）。

## Acceptance tests

- **T-165** 一個 ext4 檔案系統空間剩 40%，但 inode 用完。 → 磁碟資訊標出 inode 耗盡；需要建檔的工作在預檢時被擋下並寫出原因。
- **T-183** 主機 PID 使用率達 92%。 → 節點頁的資源資訊標出並告警。告警規則與通知在 081。

T-165 的畫面部分：檔案系統卡片標「inode 用盡」，頁面上方的「有資源快用完了」寫出哪個掛載點、還有空間但無法建立新檔案（`overview.test.tsx`「flags PIDs over 90 % and a filesystem out of inodes…」）。預檢擋下工作的部分未做。T-183 的畫面部分：程序數 92% 時列出「程序數用了 92.0%，超過 90%」（同一條測試）；告警規則與通知在 081。

## 設計缺口

1. **主機頁頁首**：畫板的「終端機」「重新啟動 agent」「部署到此主機」按鈕屬於其他票，沒放。
2. **主機頁分頁**：畫板有概況、系統、容器、磁碟、檔案、日誌、終端機、變更帳本 8 個分頁；只做了概況與系統，其他分頁等各自的票。票 125 的身分、連線、憑證、維護面板沒有畫板，暫放在「系統」分頁，請設計端決定它們的位置。
3. **概況頂部的事實列**：畫板的「執行階段 Docker 27.3.1」「Agent 版本 · mTLS」「角色 控制中心 · 資料主機」「GPU」不在 020.1 的主機資訊 API；執行階段在 039.1、Agent 版本在主機的元件清單，角色沒有 API。沒放。
4. **CPU 卡片**：畫板寫時脈（3.5 GHz），API 沒有。沒放。
5. **GPU 卡片與 GPU 區塊**（裝置詳細、使用中的程序、GPU 趨勢、容器 GPU 授權）：資料在 020.2。沒放。
6. **溫度來源**：畫板列 smartctl、NVML 等來源，Agent 目前只回報 hwmon 與 thermal zone。
7. **CPU 趨勢的「最高（單核）」序列**：歷史 API 只有每核的序列，沒有「各核最高」；要畫得逐核讀再算，30 天時請求量太大。只畫平均。
8. **部署標記**（「部署標記來自工作中心」）：沒有 API。沒畫。
9. **記憶體趨勢**：畫板是「已用／快取／可用」堆疊面積，但 API 的「可用」已經包含快取，堆起來會重複計算。改成三條線，請設計端決定是否改成「已用／可用」兩段堆疊。
10. **磁碟使用表**（掛載點、裝置身分、已綁定）：屬於 030.2 與 032。概況只放檔案系統卡片。
11. **最熱容器、程序**：屬於 040 與 023。沒放。
12. **狀態畫面**：畫板沒有畫「從未回報」「資料過期」「這段時間沒有資料」「有資源快用完了」這幾個狀態，實作照 DESIGN.md 的文字規則做，請補畫。
13. **唯讀掛載**：Core 的 `exhaustion` 把所有唯讀掛載都算成耗盡；畫面只在該列標「唯讀」、不列入告警。要不要告警、哪些掛載該告警，需要產品與設計決定（Core 端也要對應調整）。

## Notes

- （PR #161 審查交過來，2026-11-14）`hostmetrics.Store.RunPruner` 丟掉 `Prune` 的錯誤，清除失敗時沒有任何紀錄；接上平台日誌或健康訊號時一起處理。
- （同上）每個樣本點在同一個交易裡要兩條語句（原始點與 5 分鐘彙總），平台資料庫只有一個寫入連線。幾十台主機沒問題，100 台以上要先量：每台每 10 秒一則報告時的交易時間，以及 API 讀取被排隊的延遲。
- （2026-11-14，主機頁實作）還沒做：總覽頁（畫板 Overview）的主機趨勢；工作預檢擋下 inode 用盡或唯讀的檔案系統（工作引擎，不在 `web/`）。下一個人從這兩項接手。
- （同上）Core 的 OpenAPI 文件沒有把 Go 指標欄位標成可為 null，產生的型別說這些欄位一定有值，但 Core 實際會送 null。`web/src/nodes/monitor/api.ts` 用 `Maybe<T>` 放寬；之後 Core 產生 OpenAPI 時應該補上 nullable。
- （同上）Core 的 `hostmetrics.Assess` 把每個唯讀掛載都算成耗盡；容器、snap、ISO 的唯讀掛載是刻意的，畫面因此只在該列標「唯讀」、不列入告警。預檢與告警（081）要決定哪些唯讀掛載算問題。
- （同上）CPU 趨勢的「最高（單核）」：歷史 API 只有每核序列，逐核讀 30 天要多倍請求。Core 若加一條各核最高的彙總序列，畫面就能補上。
- 2026-11-14（規劃端審查 PR #181）：Core 的 OpenAPI 文件沒有把會回 null 的指標欄位標成 nullable，前端在 `web/src/nodes/monitor/api.ts` 用 `Maybe<T>` 把所有欄位放寬成可能為 null。之後每個讀這類 API 的畫面都要重做一次。修正點在 Core 產生 OpenAPI 的地方（指標型別標 nullable），修好後拿掉 `Maybe`。
