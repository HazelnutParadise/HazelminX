# 107 — 維運者可以看到每個資源由誰管理、與平台紀錄差在哪，並在寫入前看到影響範圍

**Epic:** 基礎建設（`epic:foundation`）  
**User Story:** 維運者可以信任畫面上的狀態，並安全處理外部變更  
**Milestone:** M1 單機主機管理  
**Blocked by:** 007 Core 與 Agent 可以用版本化、雙向驗證的通道交換能力與工作事件, 008 使用者可以提交工作後關閉頁面，之後仍能查到進度、證據與結果, 010 整合者可以用 /management/v1 的分頁、版本條件與工作回應操作資源  
**規格章節:** 增補 03｜51｜異常情境的整體處理  
**Issue:** [#114](https://github.com/HazelnutParadise/hazelminx/issues/114)  

## What it delivers

所有受管資源共用的狀態模型與依賴圖：控制者、現場與平台記錄不同（漂移）、觀測時間、鎖；漂移的採納、還原、保留唯讀；寫入前從同一份依賴圖算出影響；名稱、主機名、IP 歷史；偵測同主機的其他管理工具。畫面上以資源狀態條與影響預覽兩個共用元件呈現。細化 ARC-005 與規格 34.2。

## Acceptance criteria

- [ ] **ROB-001**（增補 03）維運者可以在每個受管資源看到控制者、接管狀態、漂移、觀測時間與鎖（細化 ARC-005、34.2）。 — 完成條件：機制一清單內的每種資源都有資源狀態條；漂移列出差異欄位；能不能寫入依機制一的「控制者與能不能寫入」表；偵測到控制者衝突時，標出實際生效的一方並唯讀，選定後依機制一的流程處理。畫面停用的寫入，API 一律拒絕並回傳錯誤代碼。
- [ ] **ROB-002**（增補 03）維運者可以對任何受管資源的漂移選擇採納、還原或保留唯讀（把 34.2 推廣到所有資源類型）。 — 完成條件：平台不自動改回；還原走變更計畫與差異預覽，資源不可寫入時停用；現場已不存在時，採納會標「已在平台外移除」；保留唯讀後依 44.2 可再接管。
- [ ] **ROB-003**（增補 03）系統在寫入前，從機制二的單一依賴圖算出受影響的對象並呈現。 — 完成條件：每個會改變受管資源的 `/management/v1` 端點都提供影響預覽：可以在該端點加上查詢參數 `dryRun=true` 取得，變更計畫（36.2 `POST /management/v1/change-plans`）回應的「影響」欄也來自同一份資料；API 文件逐一標記這些端點，作為核對清單；被引用的項目不能刪除並列出引用者，引用者全在同一次刪除範圍內時不擋；NOD-009 的不再管理與移除 Agent 不受阻擋。
- [ ] **ROB-006**（增補 03）系統保留資源的名稱、主機名與 IP 歷史，並依機制五判定容器屬於哪個服務。 — 完成條件：改名或換 IP 後歷史與告警仍連到同一資源；機制五表格的七種情況各自判定正確。
- [ ] **ROB-012**（增補 03）系統可以持續偵測同一主機上的其他管理工具，並標出它們控制的資源（細化 INS-014，從安裝時延伸到持續偵測）。 — 完成條件：1Panel、Portainer、certbot 依已知特徵判定控制的資源（systemd 服務、資料目錄、Compose 工作目錄、容器標籤），判定規則寫在各工具的 adapter；例如 Compose 工作目錄位於 1Panel 安裝目錄的 `apps/` 底下，就判定由 1Panel 控制。Helm 依 Kubernetes 資源的管理標註判定，但經 KUB-007 安裝的 release 控制者是 HazelminX。Cockpit 與 Webmin 直接修改系統檔，沒有可對應到個別資源的紀錄，所以只列在節點頁的元件清單，不指派為任何資源的控制者。判定不出來的容器與 Kubernetes 資源標「控制者不明」，不猜。
- [ ] （增補 03 51.6）設計時決定並寫進本票：可排隊與直接拒絕的動作清單、排隊工作的預設過期時間（實作時修改票 008 已完成的工作引擎）；「同一張憑證」的判定方式（與 057 共同）。
- [ ] （後續事項 2026-11-11）寫入閘門的 `RESOURCE_READ_ONLY`、`CONTROLLER_CONFLICT`、`SCOPE_DEGRADED`、`RESOURCE_REFERENCED` 各有一條經 API 被拒絕的測試；目前只有單元測試。第一個有受管資源端點的票接上 `ResourceState` 時補。

## Acceptance tests

- **T-157** 在主機上用 `docker rm` 刪掉平台管理的容器。 → 下一次觀測（預設 60 秒內）該服務標「實例缺失」。提供還原（走變更計畫）、採納（標「已在平台外移除」）、保留唯讀。平台不自動重建。
- **T-158** 主機上裝著 1Panel（預設安裝目錄），用 Compose 部署了 3 個應用容器。 → 節點頁的元件清單列出 1Panel；這 3 個容器的控制者標 1Panel，接管狀態「唯讀觀察中」，平台不能寫入；接管要依 44.1、44.2 的程序。
- **T-159** 先查看「停止 Zentinel」的影響，再查看「重開機 Zentinel 所在節點」的影響。 → 重開機列出的項目包含停止 Zentinel 列出的全部站點。
- **T-162** 節點改主機名並換 IP。 → 仍是同一個節點；顯示曾用名與曾用 IP；舊告警仍連到它。
- **T-169** 平台部署的服務重新部署（容器重建）。 → 服務的歷史、告警與站點路由連續，不被當成新資源。
- **T-170** certbot 與 Zentinel 都在續同一張憑證。 → 憑證標「控制者衝突」並寫出實際生效的一方；在管理員選定前，平台的續期與編輯動作停用，API 拒絕。選定 HazelminX 後產生移交計畫，批准前不停用 certbot。
- **T-173** 主機上有一個沒有平台標籤、也不屬於任何已知工具的容器。 → 控制者標「控制者不明」，平台不能寫入；不猜成任何工具。
- **T-176** 刪除整個 Compose 專案並選擇連同資料刪除（APP-008、UI-009），其中一個儲存卷另被專案外的備份任務引用。 → 專案內只被專案內容器引用的網路與儲存卷照常刪除；被備份任務引用的儲存卷不刪並列出引用者；結果逐項列出。
- **T-177** 一台現成主機上有發行版內建的 nginx.service 與管理員手寫的 ufw 規則。 → 兩者控制者為「作業系統」，可以直接用 SYS 系列功能修改；之後有人在主機上改動時標為漂移。
