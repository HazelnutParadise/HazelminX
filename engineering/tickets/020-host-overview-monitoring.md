**Blocked by:** 019 管理員可以用一次性註冊碼加入節點，並看到離線、過期、維護與撤銷狀態, 017 使用者可以在主導覽、全域搜尋與工作中心之間完成日常操作

**Issue:** [#20](https://github.com/HazelnutParadise/hazelminx/issues/20)  

## What it delivers

這張票是索引，自己不交付內容，四張子票都在 `done/` 時一起關閉。拆分原因：Agent 收集、Core 保存與 API、GPU、需要高權限執行器的磁碟健康、前端畫面分屬不同元件，一個 PR 做不完也驗不完。

| 項目 | 子票 |
|---|---|
| 主機資訊（OS、核心、架構、開機時間、時區、時間同步）；CPU 每核心、記憶體（快取不算成不可用）、swap、負載、PSI、PID 與檔案描述元、檔案系統容量與 inode、磁碟延遲與 I/O 與分類、網路、hwmon 溫度；Core 保存有解析度的歷史、保留缺口、`/management/v1` API；Agent 監控迴圈的資源量測（SYS-001、MON-001、MON-005 後端、MON-003 延遲／I/O／容量、ROB-009 指標、T-172） | 020.1 |
| GPU 指標與欄位對齊 1Panel、GPU 程序對回容器（MON-002） | 020.2 |
| 磁碟健康與 SMART、USB bridge 明示、smartctl／nvme／IPMI 溫度（MON-003 健康） | 020.3 |
| 主機頁與總覽畫面、硬體卡片、趨勢圖；工作預檢擋下 inode 用盡與唯讀（T-165、T-183） | 020.4 |

## Notes

### 設計審查留下的項目

- 宿主機系統頁與主機頁偏長：分頁各自載入，第一屏只放套件與服務（與票 017 共同處理）。
- （後續事項 2026-11-11）Issue #20 原本比這份票檔多出幾條驗收：GPU 欄位對齊 1Panel、GPU 程序對回所屬容器、硬體依類別分組成卡片、ROB-009，以及驗收案例 T-165、T-172、T-183。票檔是驗收條件的唯一來源，issue 內文在 2026-11-11 已經從票檔重新產生，所以這幾條現在只記在這裡。動工前要決定把它們補進驗收條件，或確定不做。
- （後續事項 2026-11-11）Agent 的命令層（Komodo `lib/command`）由票 020、040、044 中最先動工的那張移植（`agent/UPSTREAM.md`）。
- （票 019 交過來，PR #143 審查 2026-11-12）主機與註冊碼清單目前是整張表讀進記憶體，再篩選、排序、分頁（`nodereg.Registry.ListNodes`、`ListEnrollments`）。`node_enrollments` 的資料列從不清除，每產生一個註冊碼就多一列。
  - 實測（開發機，`go test`）：註冊碼 1,000 列約 9 毫秒，10,000 列約 78 毫秒，30,000 列約 250 毫秒；主機 1,000 台約 13 毫秒，時間大致隨列數線性增加。
  - 平台資料庫只有一個連線，清單讀取期間其他寫入都要排隊。主機頁或狀態列若每幾秒輪詢一次清單，註冊碼累積到上萬列時就會拖慢整個平台。
  - 建議：篩選、排序與分頁改由 SQL 做（`state`、`created_at` 加索引，沿用 `api` 的 keyset 分頁），並定期清除已過期、已拒絕或已收回超過保留期限（例如 90 天，稽核紀錄另有保存）的註冊碼列。
