# 規格增補 03｜異常情境的整體處理

- 狀態：已核定（2026-11-07）。
- 位置：接在增補 02（50 章）之後，章節編號 51。需求 ID 以 `ROB-` 開頭，驗收案例 `T-157` 起。
- 範圍：v1.1 已有處理異常的機制，散在不同章節：控制者與接管（ARC-005、CTR-009、44.2）、現場與平台記錄不同（34.2）、工作引擎與鎖（33 章）、告警去重（MON-004）、失敗情境（40 章）。本章不重寫它們，只做兩件事：
  1. 把這些機制推廣到所有資源類型，並規定畫面上用同一組元件呈現；
  2. 補上既有規格沒有涵蓋的部分。

## 51.1 原則：用少數機制涵蓋大量情境

逐一為每個怪情況加一個橫幅、按鈕或規則，畫面會越來越吵，實作也會出現互相矛盾的特例。本章的做法：

1. 先判斷這個情況屬於哪一類「系統不知道的事」：不知道誰改的、不知道資料是不是最新、不知道會影響誰、不知道平台自己還能不能用、不知道是哪一個、不知道總共有多少。
2. 每一類由一個機制處理，畫面上用同一個元件呈現。
3. 情境總表（51.4）只用來證明「每個情境都有去處」。必做的行為一律寫在需求（51.3）或既有需求裡，總表不另外定義新行為。

## 51.2 六個機制

### 機制一：資源狀態（誰控制、資料是不是最新、有沒有人在動）

細化 ARC-005 與 34.2，適用於所有受管資源：容器、Compose 專案、站點、憑證、防火牆規則、排程、模組設定、資料庫、備份任務。

| 欄位 | 內容 | 既有依據 |
|---|---|---|
| 控制者 | HazelminX、外部工具（1Panel、Portainer、Webmin、Cockpit、certbot、Helm…）、叢集控制器，或「未接管」 | ARC-005 的擁有者欄、44.2 |
| 現場與平台記錄不同 | 平台最後套用的設定與現場觀測不一致；本章簡稱「漂移」 | 34.2 |
| 觀測時間 | 資料從現場讀到的時間 | UI-007、NOD-007 |
| 鎖 | 目前佔用該資源的工作 | ENG-004、33.2 |

「控制者」是 ARC-005 的「擁有者」欄位。本章改用「控制者」，是為了不跟 5.1 的「擁有者」角色、增補 02 環境的擁有者（root 或某個 Linux 使用者）撞名。

漂移的處理沿用 34.2 的三個選擇，永遠不自動改回：

- **採納**：平台記錄改成現場的樣子。如果現場的資源已經不存在，採納等於在平台記錄標為「已在平台外移除」，並保留歷史。
- **還原**：把現場改回平台記錄，走變更計畫與差異預覽。
- **保留唯讀**：控制者改為外部或「未接管」，平台對該資源只讀。之後要再接管，依 CTR-009 與 44.2 辦理。

### 機制二：單一影響圖

所有寫入動作在送出前，都從同一份依賴圖算出受影響的對象。既有需求裡各自列影響的地方，改由這份圖提供資料：SYS-010（重開機）、NOD-008（維護模式）、CTR-005（映像引用）、CTR-007（網路使用）。

**依賴圖的定義**

- 邊有方向，寫成「A 依賴 B」，代表 B 停止或刪除時 A 會受影響。例如：站點依賴容器，容器依賴儲存卷，備份任務依賴儲存卷，排程依賴容器。
- 節點類型：節點、引擎環境、容器、Compose 專案、服務、儲存卷、網路、映像、站點、憑證、Zentinel 入口、systemd 服務、模組、資料庫、備份任務、排程、權杖、工作。
- 「被引用」指的是：有其他節點依賴這個節點。

### 機制三：用途等級

節點與專案可以標為「正式」「測試」或「實驗」。一個資源的有效等級，取它所屬節點與專案之中較嚴格的那個，順序是正式 > 測試 > 實驗。例如節點是正式、專案是測試，有效等級就是正式。

用途等級不改變權限，只改變三件事：頁首的等級徽章、確認框的內容、終端機分頁的標示。

這和增補 02 的「引擎環境」是兩回事：引擎環境是一個 Docker 或 Podman 執行端點，用途等級是這份資源拿來做什麼。

### 機制四：降級模式

平台自身或依賴的元件壞掉時，依下表決定還能做什麼。降級時在頂列下方顯示降級列，寫出壞掉的是什麼；不能做的動作停用，並在提示寫出原因。

| 壞掉的東西 | 觸發條件（預設值，可調） | 還能做 | 不能做 |
|---|---|---|---|
| 平台資料庫唯讀或損毀 | 寫入失敗，或完整性檢查失敗 | 唯讀瀏覽、下載診斷包、依 INT-002 用 CLI 救援 | 任何寫入 |
| 平台資料磁碟剩餘不足 | 平台資料目錄所在檔案系統剩餘 < 5% 或 < 2 GiB | 讀取，以及新增清理類、搬移類工作 | 其他新工作與上傳 |
| 某節點離線 | 超過 NOD-007 的離線判定 | 看上次觀測 | 對該節點的寫入（按鈕不隱藏，寫出原因） |
| 某引擎環境停止 | 端點無回應 | 看設定與日誌檔、修復引擎 | 該環境的容器操作 |
| 節點時間偏差 | 節點與 Core 的時間差 > 120 秒 | 讀取 | 對該節點的排程與憑證簽發 |
| Core 自身時間偏差 | Core 與 NTP 差 > 60 秒 | 全部照常，同時告警 | 無（不停用登入，避免 TOTP 全部失效時被鎖在外面） |

「平台資料磁碟剩餘不足」與 35.3 的關係：35.3 管日誌與流量紀錄的預算；這裡管平台本身能不能繼續寫入，兩者分開觸發。

Core 停止時沒有畫面可以顯示，不屬於本機制。這時的行為依 ARC-002：已運行的網站照常服務；Agent 依 JOB-012 執行預先授權的本地工作。

### 機制五：身分與名稱

- 資源以持久 ID 識別（沿用 NOD-005）。改名、改主機名、換 IP 時保留歷史，畫面顯示曾用名。
- 平台管理的服務與 Compose 專案是長期存在的邏輯資源。平台自己部署或還原時重建了容器，歷史與告警仍掛在同一個服務上（呼應 WEB-003）。
- 在平台以外建立、只是剛好同名的容器，視為新資源，歷史不混在一起。
- 名稱類欄位（容器名、檔名、標籤、主機名）一律完整呈現：控制字元可見化，非 UTF-8 以替代字元顯示並可檢視原始位元組，超長時換行而不截斷。
- 日誌與檔案內容仍依 UI-012、FIL-004 的大小上限分段呈現，不受上一條「不截斷」限制。

### 機制六：量的邊界

`/management/v1` 的每個列表端點，以及 UI 的每個表格，都要宣告每頁筆數、查詢上限與逾時。超過時寫出「已顯示 N 筆／總數 M」；如果是逾時，寫「總數未知」，保留已取得的部分，並提供「改成背景工作」，讓查詢以工作的形式在背景跑完。

## 51.3 要求

| ID | 誰可以做什麼與必要行為 | 可檢驗的完成條件 |
|---|---|---|
| ROB-001 | 維運者可以在每個受管資源看到控制者、漂移、觀測時間與鎖（細化 ARC-005、34.2）。 | 四件事出現在同一條資源狀態條，適用 51.2 機制一列出的所有資源類型；漂移列出差異欄位。同一資源偵測到兩個控制者時（例如 certbot 與 Zentinel 都在續同一張憑證），狀態條標「控制者衝突」並寫出實際生效的是哪一方。 |
| ROB-002 | 維運者可以對任何資源類型的漂移選擇採納、還原或保留唯讀（把 34.2 推廣到所有資源類型）。 | 平台不自動改回現場。還原走變更計畫與差異預覽。現場資源已不存在時，採納會把平台記錄標為「已在平台外移除」。保留唯讀後，可依 CTR-009 再接管。 |
| ROB-003 | 系統在寫入前，從 51.2 機制二定義的單一依賴圖算出受影響的對象並呈現。 | 下列動作全部使用同一份圖：停止、重啟、刪除、升級、重開機、進入維護、移除引擎、撤銷權杖、改 Port、停用模組；新增的寫入動作也必須接上。被引用的資源，刪除鈕停用並列出引用者。 |
| ROB-004 | 使用者可以知道平台目前是否在降級模式，以及還能做什麼。 | 依 51.2 機制四的表與預設門檻切換。降級列只在降級時出現；不能做的動作停用，並寫出原因。 |
| ROB-005 | 管理員可以為節點與專案標示正式、測試或實驗的用途等級。 | 有效等級依機制三計算，出現在頁首、確認框與終端機分頁；對正式等級資源的寫入，確認框寫出等級與目標名稱。 |
| ROB-006 | 系統保留資源的名稱、主機名與 IP 歷史，並區分邏輯資源與執行實例。 | 改名或換 IP 後，歷史與告警仍連到同一資源。平台部署或還原時重建的容器，歷史掛在同一個服務上。平台以外建立的同名容器視為新資源。 |
| ROB-007 | 使用者看到的名稱類欄位完整且安全。 | 控制字元可見化；非 UTF-8 檔名可以顯示、改名、下載，並可檢視原始位元組；超長名稱換行而不截斷。 |
| ROB-008 | 每個列表與查詢宣告其邊界，並在超出時說明。 | 範圍是 `/management/v1` 的列表端點與 UI 表格。顯示已顯示筆數與總數，或「總數未知」。逾時時保留已取得的部分，並可改成背景工作，進度在工作中心查看。 |
| ROB-009 | 維運者可以看到「看起來還有空間卻不能用」的耗盡狀態（補足 MON-001、STO-001、STO-010）。 | 監控 PID 數、檔案描述元、記憶體壓力，以及檔案系統被重新掛成唯讀。記憶體壓力用 Linux PSI 的 `some avg60`，預設 > 10% 告警。容器被 OOM 終止時，事件寫出原因與記憶體限制。新增檔案或寫入資料的工作，預檢時擋下 inode 用盡或唯讀的檔案系統，並寫出原因。 |
| ROB-010 | 可能切斷管理路徑的變更，在套用前檢查、套用後確認（細化 SYS-008、SSH-003、SET-002、HSM-011）。 | 管理路徑指：瀏覽器到 Core 管理入口、Core 到 Agent 的通道、維運者使用的 SSH。防火牆、管理入口 Port、平台 TLS、sshd、PAM、網路設定，套用前檢查這三條路徑。套用後由節點本機計時，預設 60 秒內未確認就自動回復；不依賴可能已斷線的 Core。 |
| ROB-012 | 系統可以偵測同一主機上的其他管理工具，並標出它們控制的資源。 | 依各工具的已知特徵判定：systemd 服務、資料目錄、Compose 工作目錄、容器標籤，判定規則寫在各工具的 adapter。例如 Compose 工作目錄位於 1Panel 安裝目錄的 `apps/` 底下，就判定由 1Panel 控制。判斷不出來的資源標為「未接管」，不猜。被其他工具控制的資源，在接管前保持唯讀。 |

ROB-011 不設立：原本規劃的「告警去抖動」已由 MON-004 涵蓋（持續時間、恢復門檻、去重），只在 T-168 驗收翻轉次數的呈現。

## 51.5 驗收案例

| ID | 情境 | 預期 |
|---|---|---|
| T-157 | 在主機上用 `docker rm` 刪掉平台管理的容器。 | 下次觀測時標為漂移。提供還原（走變更計畫）、採納（平台記錄標「已在平台外移除」）、保留唯讀；平台不自動重建。 |
| T-158 | 主機上裝著 1Panel（預設安裝目錄），它用 Compose 部署了 3 個應用容器。 | 節點的元件矩陣列出 1Panel。這 3 個容器的控制者標 1Panel、保持唯讀，直到依 CTR-009 接管。 |
| T-159 | 停止 Zentinel 前查看影響。 | 影響預覽列出所有依賴它的站點與憑證；與刪除、重開機時看到的影響來自同一份依賴圖。 |
| T-160 | 平台資料庫變成唯讀。 | 出現降級列；寫入按鈕停用並寫出原因；可以下載診斷包；依 INT-002 可用 CLI 救援。 |
| T-161 | 節點標正式、專案標測試，對該專案按部署。 | 有效等級為正式；確認框寫出「正式」與專案、節點名稱。 |
| T-162 | 節點改主機名並換 IP。 | 仍是同一個節點；顯示曾用名與曾用 IP；舊告警仍連到它。 |
| T-163 | 資料夾裡有非 UTF-8 檔名。 | 可以列出、改名、下載，並可檢視原始位元組。 |
| T-164 | 查詢 1 萬筆容器事件時逾時。 | 顯示已取得筆數與「總數未知」；可改成背景工作，在工作中心看到結果。 |
| T-165 | 磁碟空間剩 40%，但 inode 用完。 | 磁碟卡標出 inode 耗盡；新增檔案的工作在預檢時被擋下並寫出原因。 |
| T-166 | 容器被 OOM 終止。 | 事件寫出 OOMKilled 與記憶體限制，連到該容器。 |
| T-167 | 套用一條會擋掉管理入口的防火牆規則（使用預設逾時）。 | 套用前警告；套用後 60 秒內沒確認，由節點本機自動回復。 |
| T-168 | 節點在 MON-004 設定的時間窗內上下線 8 次。 | 合併成一個事件並標出翻轉 8 次，不發 8 則告警。 |
| T-169 | 一個由平台部署的服務重新部署（容器重建）。 | 服務的歷史、告警與站點路由連續，不被當成新資源。 |

## 51.6 刻意不做的事

- 不為每個情境做專屬橫幅或頁面。一律由資源狀態條、降級列、影響預覽、用途等級徽章四個元件承接。
- 不自動修復漂移，因為現場的狀態可能才是對的。
- 不用 AI 推測異常原因並寫成句子。畫面只呈現能從資料直接得到的內容。
- 不攔截 root 終端機裡的指令。攔不完整，反而給人錯誤的安全感。
