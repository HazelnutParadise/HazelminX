# 規格增補 03｜異常情境的整體處理

- 狀態：已核定（2026-11-07）。
- 位置：接在增補 02（50 章）之後，章節編號 51。需求 ID 以 `ROB-` 開頭，驗收案例 `T-157` 起。
- 範圍：v1.1 已有處理異常的機制，散在不同章節：
  - 控制者與接管：ARC-005、CTR-009、44.1、44.2
  - 現場與平台記錄不同：34.2
  - 資料模型與永久識別碼：34.1、第 7 章
  - 工作引擎與鎖：33 章
  - 告警去重：MON-004
  - API 規則：36 章
  - 失敗情境：40 章

  本章不重寫這些機制，只做兩件事：
  1. 把它們推廣到所有資源類型，並規定畫面與 API 用同一套規則呈現。
  2. 補上既有規格沒有涵蓋的部分。

## 51.1 原則：用少數機制涵蓋大量情境

逐一為每個怪情況加一個橫幅、按鈕或規則，畫面會越來越吵，實作也會出現互相矛盾的特例。本章把異常歸成六類「系統不確定的事」，每類由一個機制處理：

| 系統不確定的事 | 機制 |
|---|---|
| 誰在控制、資料是不是最新、現在有沒有工作佔用 | 一、資源狀態 |
| 動了它會影響誰 | 二、單一影響圖 |
| 它是正式還是測試用途 | 三、用途等級 |
| 平台自己還能做什麼 | 四、降級模式 |
| 它到底是哪一個 | 五、身分與名稱 |
| 總共有多少、是不是全部 | 六、量的邊界 |

必做的行為一律寫在 51.1～51.3 或既有需求裡。51.4 的情境總表只用來證明每個情境都有去處，不另外定義新行為。

畫面上新增五個共用元件：

- **資源狀態條**：放控制者、接管狀態、漂移、觀測時間、鎖、用途等級，以及節點或引擎環境層級的降級。有兩種形式：有獨立頁面的資源，放在頁面標題區下方的一整列；只出現在列表裡的資源（例如防火牆規則、對外 Port、Linux 使用者、排程），在名稱旁顯示精簡圖示，只標出異常項（漂移、鎖、控制者不是 HazelminX 或作業系統、已保留唯讀、控制者衝突、正式等級、降級），停留可看完整內容。
- **影響預覽**：寫入前列出受影響對象的面板。
- **降級列**：平台降級時，出現在全站頂端導覽列下方的一列。
- **用途等級徽章**。
- **套用確認倒數**：ROB-010 的變更套用後，倒數等待確認。

其餘畫面沿用既有元件，例如編輯器衝突提示（FIL-004）、工作中心（UI-003 的工作列表）、磁碟資訊（STO-001 的磁碟頁）、節點頁的元件清單（列出 Agent、Zentinel、節點憑證與偵測到的其他管理工具）。

本章所有「停用」「唯讀」「擋下」的規則，畫面上是按鈕停用並寫出原因；`/management/v1` 同一個動作則拒絕執行，並回傳下表的錯誤代碼，格式沿用 36.2 的大寫底線寫法（36 章：網頁禁止的事，API 也不能做）。

| 錯誤代碼 | HTTP 狀態 | 意思 |
|---|---|---|
| `RESOURCE_READ_ONLY` | 409 | 依機制一「控制者與能不能寫入」表，資源目前不可寫入 |
| `CONTROLLER_CONFLICT` | 409 | 資源偵測到控制者衝突，尚未選定 |
| `RESOURCE_REFERENCED` | 409 | 項目被範圍外的項目引用，不能刪除；回應列出引用者 |
| `PLATFORM_DEGRADED` | 503 | 平台層級降級，回應寫出是哪一種 |
| `SCOPE_DEGRADED` | 409 | 目標節點或引擎環境降級，回應寫出是哪一種；可排隊的工作改回 202 並標「排隊中」 |
| `CONFIRMATION_REQUIRED` | 409 | ROB-010 的變更還在等確認，同一資源的其他變更暫時不能送出 |

## 51.2 六個機制

### 機制一：資源狀態

細化 ARC-005 與 34.2。「受管資源」指以下類型：

- 節點、引擎環境、磁碟、檔案系統與掛載
- 容器、Compose 專案、服務、儲存卷、網路、映像
- 站點、憑證、Zentinel 入口
- 防火牆規則與對外 Port
- systemd 服務、Linux 使用者、模組設定、主機排程（crontab、systemd timer）
- 平台計畫任務（28 章）
- 資料庫、備份任務
- Kubernetes 資源

每個受管資源帶以下欄位：

| 欄位 | 內容 | 既有依據 |
|---|---|---|
| 控制者 | 下列其中一個：<br>• HazelminX<br>• 作業系統：主機上原本就有、沒被任何工具宣告的資源<br>• 某個外部工具（1Panel、Portainer、certbot、Helm…）<br>• 叢集控制器<br>• 控制者不明 | ARC-005 的擁有者欄 |
| 接管狀態 | 不適用、唯讀觀察中、已接管、已保留唯讀 | ARC-005、CTR-009 |
| 漂移 | 平台最後套用或首次觀測的設定，與現場觀測不一致 | 34.2「現場與平台記錄不同」 |
| 觀測時間 | 設定與狀態從現場讀到的時間；預設每 60 秒觀測一次（本章新增的預設值；監控指標依 38 章另有頻率） | UI-007、NOD-007 |
| 鎖 | 目前佔用該資源的工作 | ENG-004、33.2 |

「控制者」就是 ARC-005 的「擁有者」欄位；ARC-005 的「來源」「控制世代」照舊保存，在資源詳細資料中呈現，不放進狀態條。本章改用「控制者」，是為了不跟 5.1 的「擁有者」角色、增補 02 環境的擁有者（root 或某個 Linux 使用者）撞名。

**控制者與能不能寫入**

| 控制者 | 接管狀態 | 平台能不能寫入 |
|---|---|---|
| HazelminX（平台建立，或經 KUB-007 安裝的 Helm release） | 不適用 | 可以 |
| 作業系統（例如發行版內建的 systemd 服務、管理員手寫的防火牆規則、crontab、模組設定） | 不適用 | 可以；SYS、HSM 系列需求照常運作，仍偵測漂移 |
| 外部工具 | 唯讀觀察中 | 不可以 |
| 外部工具 | 已接管（控制者改為 HazelminX） | 可以 |
| 叢集控制器 | 唯讀觀察中 | 不可以；不提供接管，要改真正的來源（44.2） |
| 任何控制者 | 已保留唯讀（控制者維持原值） | 不可以；再接管後，控制者改為 HazelminX，接管狀態改為已接管 |
| 控制者不明 | 唯讀觀察中 | 不可以 |
| 控制者不明 | 已接管（控制者改為 HazelminX） | 可以 |

控制者衝突時，不論表中哪一列都不可寫入。增補 02 ENV-004 的叢集節點容器也屬於叢集控制器，不提供接管。

判斷不出控制者時，先依 ROB-012 判定；仍判定不出來：

- 引擎物件（容器、Compose 專案、儲存卷、網路、映像）與 Kubernetes 資源，標「控制者不明」、接管狀態「唯讀觀察中」，與 44.2「現有資源先唯讀檢視」一致；要寫入（包括清理未使用的映像）須先依 CTR-009 接管，可整批接管。引擎內建的網路（例如 `bridge`、`host`、`none`）不能刪除，也不需要接管。
- 其他主機層級的資源（systemd 服務、Linux 使用者、防火牆規則、主機排程、模組設定、磁碟與掛載），歸為「作業系統」。

**控制者衝突**

同一資源偵測到兩個控制者時，例如 certbot 與 Zentinel 都在續同一張憑證：

- 標為「控制者衝突」，並寫出實際生效的是哪一方。
- 在管理員選定之前，平台對該資源只讀（ARC-005：兩個控制器不能同時寫入）。
- 選定 HazelminX 時，平台產生移交計畫，列出要停用的對方設定（例如 certbot 的續期排程），經批准才執行（INS-014：沒有移交批准不停止其他工具）。
- 選定對方時，控制者設為被選定的一方，接管狀態設為「已保留唯讀」，平台停用自己對該資源的寫入（例如 Zentinel 的續期），並清除衝突標記。
- 「控制者衝突」是一個標記，不是接管狀態；接管狀態維持原值。

**漂移的處理**

沿用 34.2 的三個選擇，永遠不自動改回：

- **採納**：平台記錄改成現場的樣子。如果現場的資源已經不存在，平台記錄標為「已在平台外移除」，並保留歷史。
- **還原**：把現場改回平台記錄，走變更計畫與差異預覽。資源目前不可寫入時（唯讀觀察中、已保留唯讀、控制者衝突），還原停用，只能採納，或先接管、選定控制者。
- **保留唯讀**：接管狀態改為「已保留唯讀」。

**再次接管**

所有資源類型都依 44.2 的程序：先唯讀檢視，記錄原設定，再選擇接管。接管時，以當下的現場狀態作為新的平台記錄（等同採納）。從 1Panel 移交時，另依 44.1 的順序：先確認網站與資料可用，再停止原工具對該資源的自動排程。

### 機制二：單一影響圖

所有寫入動作在送出前，都從同一份依賴圖算出受影響的對象。既有需求裡各自列影響的地方，改由這份圖提供資料：

- UI-006：設定差異與受影響服務
- SYS-010：重開機
- NOD-008：維護模式
- CTR-005：映像引用
- CTR-007：網路使用
- HSM-003：移除模組前列出引用

**依賴圖的定義**

- 圖上的每一個點稱為「項目」，避免跟主機的「節點」混淆。項目類型是機制一的受管資源，再加上 API 權杖（34.1）與工作。
- 邊只有一種意思：「A 使用 B」。B 停止或設定變更時，A 會受影響；B 被 A 使用時，B 不能刪除。例如：
  - 站點使用容器、使用憑證、使用 Zentinel 入口
  - Zentinel 入口使用 Zentinel 的服務或容器
  - 容器使用儲存卷、網路、映像與所屬的引擎環境
  - 儲存卷使用檔案系統，檔案系統使用磁碟
  - 備份任務使用儲存卷或資料庫
  - 對外 Port 使用容器
  - 引擎環境與所有在某主機上的項目，使用該主機
  - 服務的可回復發布版本（34.1）使用映像，所以回復要用的映像算被引用（呼應 CTR-005）
  - 工作使用它鎖住的資源；排程與整合使用它們的 API 權杖
- 影響範圍是沿著邊找到的所有直接與間接對象，預覽上分開標示直接與間接。例如重開機某主機時，其他主機上經過它的 Zentinel 入口的站點，也列為間接影響。
- 「被引用」指的是：有其他項目使用這個項目，而且那個項目不在同一次刪除的範圍內。「同一次刪除」包括刪除整個 Compose 專案，以及 UI-009 的批次刪除。這樣刪除整個 Compose 專案時，專案內部的網路不會被自己的容器擋住。

**刪除的阻擋**

被引用的項目不能刪除，並列出引用者。批次刪除時，只擋下被範圍外引用的項目，其餘照常刪除，結果逐項列出（UI-009）。

- 這比 HSM-003、CTR-005 原本「只列出引用」更嚴格，是刻意的：先把引用者處理掉，才能刪除。
- NOD-009 的「不再管理」與「移除 Agent」不算刪除，不受這條限制。

### 機制三：用途等級

用途等級有三種：正式、測試、實驗。

- **專案環境**：沿用 34.1「專案與環境」既有的正式／測試標記，另外增加「實驗」。CMP-018 讓同一個 repo 可以有多個環境，所以等級標在環境上，不是標在專案上。
- **節點**：本章新增，節點也可以標用途等級。

一個資源的有效等級，取它所在節點與所屬專案環境之中較嚴格的那個，順序是正式 > 測試 > 實驗：

- 節點是正式、專案環境是測試，有效等級就是正式。
- 不屬於任何專案環境的資源，只看節點。
- 跨多台主機的資源（例如叢集層級的 Kubernetes 資源、由多台主機的入口提供的站點），取所有相關主機中最嚴格的等級。
- 兩邊都沒有標示時，不顯示徽章，也不改變任何確認流程。

用途等級不改變權限。34.1「正式環境權限不能被測試環境繼承放大」的隔離規則照舊。它只影響兩件事：

1. 頁面標題區、資源狀態條與終端機分頁上的等級徽章。
2. 既有確認點對正式等級的資源，會寫出等級與目標名稱。既有確認點指：UI-006 的高風險操作確認，以及 ENG-005（33 章）變更計畫的批准畫面。本機制不新增原本沒有的確認點。

用途等級和增補 02 的「環境」是兩回事。增補 02 的環境就是 34.1 的執行環境，本章稱「引擎環境」，指一個 Docker 或 Podman 執行端點。

### 機制四：降級模式

平台自身或依賴的元件壞掉時，依下表決定還能做什麼。表中沒列出的動作照常。不能做的動作在畫面上停用並寫出原因，API 也拒絕。

降級列只在「平台層級」降級時出現在全站頂端。主機沒有回應時（節點層級），全站頂端另有一條「主機狀態列」（2026-11-08 使用者決定）：與降級列分開，只佔一行，彙總寫出「N 台主機沒有回應」與前 3 台的名稱，超過時寫「＋N」，點了進到篩選好的主機清單；標為維護中的主機不算；不能關閉，主機恢復後自動消失。引擎環境層級的降級，只出現在該節點的頁面與相關資源的狀態條。

| 層級 | 壞掉的東西 | 進入條件（預設值，可調） | 解除條件 | 還能做 | 不能做 |
|---|---|---|---|---|---|
| 平台 | 平台資料庫唯讀或損毀 | 連續 3 次寫入失敗，或完整性檢查失敗 | 寫入測試連續 3 次成功；因完整性檢查失敗而進入的，另要求完整性檢查通過 | 讀取、下載診斷包、依 INT-002 用 CLI 救援；登入照常，但工作階段只存在記憶體，平台重啟後要重新登入 | 任何其他寫入 |
| 平台 | 平台資料磁碟剩餘不足 | 平台資料目錄所在檔案系統剩餘 < 5% 或 < 2 GiB | 剩餘 ≥ 8% 且 ≥ 3 GiB | 讀取，以及新增清理類、搬移類工作 | 其他新工作（包含排程觸發的工作，依 JOB-005 之後補跑或跳過）與上傳 |
| 平台 | Core 時間不可信 | 已設定時間來源，但 Core 與它的差距 > 60 秒或連不上 | 連續 3 次對時成功且差距 < 10 秒 | 全部照常，同時告警；變更計畫批准期限（ENG-005）與工作階段到期改以 Core 的單調時鐘倒數，不受牆上時間偏差影響 | 無 |
| 節點 | 節點離線 | 超過 90 秒沒有心跳（依 38 章先顯示「過期」，滿 90 秒前寫入照常排入） | 心跳恢復並完成對帳（SEC-008） | 看上次觀測；對該節點的工作可以依 33.1 排隊 | 立即執行對該節點的寫入 |
| 節點 | 節點時間偏差 | 節點與時間來源的差距 > 120 秒（以 Agent 回報的對時狀態判定） | 差距 < 30 秒 | 讀取；編輯計畫任務 | 該節點平台計畫任務的執行；ACME 網站憑證的簽發與續期（主機排程無法由平台擋下，只告警） |
| 引擎環境 | 引擎停止或無回應 | 每次探測逾時 10 秒，連續 3 次失敗 | 連續 2 次探測成功 | 依 PKG-006、ARC-001 登入、讀日誌、執行授權的修復 | 該環境的容器操作 |

**時間來源**

時間來源可以是公開 NTP、內網 NTP，或主機自己設定的 chrony、timesyncd 來源。完全沒設定任何時間來源時，顯示「未設定時間來源」並告警，但不進入降級，避免離線安裝的環境（INS-011）永遠掛著降級列。

節點時間偏差以 Agent 回報的對時狀態判定，與 Core 的時間無關。偏差解除後，暫停期間錯過的排程依 JOB-005 決定補跑或跳過；重疊時依 JOB-004。JOB-011 處理一般偏差與夏令時間；本表只在偏差超過門檻時才擋下執行。

**兩種平台降級同時發生**

「資料庫唯讀」與「磁碟不足」同時成立時（磁碟滿常常會造成資料庫寫入失敗），以「資料庫唯讀」為準：除了 INT-002 的 CLI 救援，不能新增任何工作。清理請用 CLI 進行。

**資料庫唯讀時的稽核**

- 稽核紀錄改寫入獨立的附加檔案。安裝時預先配置固定大小的附加檔（預設 64 MiB），所以磁碟滿時仍寫得進去；安裝程式也建議把它放在另一個檔案系統。資料庫恢復後補回。
- 附加檔案也寫不進去時，拒絕新的網頁登入，已登入的工作階段轉為只能讀取，降級列寫出「稽核無法寫入」，只能用 INT-002 的 CLI 救援。CLI 救援的稽核寫入系統日誌（systemd journal）。不允許在沒有稽核的情況下操作。
- 資料庫唯讀期間，已在節點上執行的工作依 33 章由 Agent 端的持久紀錄繼續執行，結果暫存在 Agent；資料庫恢復後對帳寫回。

Core 停止時沒有畫面可以顯示，不屬於本機制。這時的行為依 ARC-002：已運行的網站照常服務，Agent 依 JOB-012 執行預先授權的本地工作。

### 機制五：身分與名稱

**永久識別碼**

資源以永久識別碼識別（第 7 章、34.1）。改名、改主機名、換 IP 時保留歷史，畫面顯示曾用名。

**容器屬於哪個服務**

平台建立的容器帶有該服務的永久識別碼標籤。比對時，服務 ID 要與平台記錄的節點、引擎環境一起相符。判定方式：

| 情況 | 判定 |
|---|---|
| 不帶標籤，但平台接管時已記錄該容器 ID（CTR-009、44.2 接管不重建容器） | 屬於接管時指定的服務 |
| 帶標籤，且平台記錄裡有這個服務，節點與引擎環境也相符 | 屬於該服務。平台部署或還原時重建，歷史與告警仍掛在同一個服務上（呼應 WEB-003） |
| 帶標籤，但設定與平台記錄不同 | 該服務的漂移 |
| 帶標籤，但數量多於服務的副本數 | 該服務的漂移（副本數不符） |
| 平台記錄的容器不見了 | 該服務的漂移：「實例缺失」 |
| 帶標籤，但平台記錄裡沒有這個服務，或節點、引擎環境不符（例如 Core 從舊備份還原、主機是複製來的） | 控制者不明，標「標籤無對應服務」 |
| 不帶標籤、沒有接管紀錄、只是剛好同名 | 新資源；先依 ROB-012 判定控制者，判定不出來才標控制者不明；歷史不混在一起 |

所以在主機上 `docker rm` 再 `docker run` 一個同名但沒有標籤的容器，會同時出現兩件事：原服務標「實例缺失」，另多一個控制者不明的新容器。

**不可信文字的呈現**

細化 36.3「日誌、檔名與容器標籤一律視為不可信文字」：

- 名稱類欄位，包括檔名、容器標籤值、主機名，一律完整呈現：
  - 控制字元、Unicode 方向控制字元（例如 U+202E）與零寬字元，以可見符號顯示。合法 emoji 序列裡的零寬連接字元（U+200D）例外，照常組成 emoji。
  - 非 UTF-8 以替代字元顯示，並可檢視原始位元組。
  - 超長時換行，不截斷。
- 日誌裡的 ANSI 色碼轉成顏色呈現；其他控制序列移除，並在原位置以符號標出。
- 日誌與檔案內容依 UI-012、FIL-004 的大小上限分段呈現，不受「不截斷」限制。

### 機制六：量的邊界

`/management/v1` 的每個列表端點，以及 UI 的每個表格，都在回應的中繼資料與表格底部寫出每頁筆數、查詢上限與逾時。預設每頁 50 筆、查詢上限 10,000 筆、逾時 15 秒，可依列表調整。

- **查詢上限**指單次查詢最多回傳的總筆數。上限以內照 36.1 正常分頁。
- 結果超過上限時寫出「可瀏覽前 N 筆／總數 M」，不能再往後翻頁，改提供「改成背景工作」。
- 逾時時寫「總數未知」，保留已取得的部分，同樣提供「改成背景工作」，讓同一個查詢以工作的形式在背景跑完，結果在工作中心查看。

**ROB-009 指標**

- **PID 使用率**：主機以 `pid_max` 為分母，容器以 cgroup 的 `pids.max` 為分母；沒設上限的容器只顯示數量。預設 > 90% 告警。
- **檔案描述元**：主機以 `file-max` 為分母，預設 > 90% 告警；容器只顯示開啟數量，不算使用率。
- **記憶體壓力**：用 Linux PSI 的 `some avg60`，主機與容器各一，預設 > 10% 告警。核心不支援 PSI 或容器在 cgroup v1 上時，標「不支援」；核心支援但 PSI 被停用時，標「未啟用」。
- **inode**：沒有固定 inode 總數的檔案系統（例如 btrfs、ZFS）標「不適用」，不算成用盡（呼應 STO-001）。
- **唯讀重新掛載**：檔案系統被重新掛成唯讀時告警。
- **OOM**：容器被 OOM 終止時，事件寫出原因與記憶體限制。
- **預檢**：需要建檔或寫入的工作，預檢時擋下 inode 用盡或唯讀的檔案系統，並寫出原因。

**ROB-010 規則**

- **管理路徑**指三條：
  - 瀏覽器到 Core 管理入口，受 SET-003 的允許來源與入口路徑管控。
  - Core 到 Agent 的通道。
  - 維運者的 SSH：sshd 目前監聽的位址與 Port，以及主機防火牆對該 Port 的允許來源。
- **套用前**：檢查變更會不會擋掉上述三條管理路徑，會擋掉時警告。預檢判定不影響管理路徑的變更（例如開放一個應用用的 Port），不套用本規則。平台無法代替維運者驗證他自己的 SSH 路徑，所以影響 SSH 的變更只警告，並要求使用者自己確認。
- **套用後**：
  - 依下表關閉操作者本人在 Core 管理入口的連線（包含 WebSocket），讓確認一定經由新連線送出；其他管理員的連線不受影響。
  - 由變更所在的主機在本機計時；Core 端設定由 Core 主機計時。
  - 時間內沒有收到下表要求的確認，就自動回復。
- **確認的方式**：在套用確認倒數上按確認，或呼叫 `POST /management/v1/confirmations/{id}`。以 API 權杖從新連線送出的確認也算數。

| 變更 | 套用後關閉的連線 | 確認條件 | 預設確認時間 |
|---|---|---|---|
| Core 主機的防火牆或網路設定 | 操作者的 Core 管理入口連線 | 使用者以新連線送出確認。Agent 通道依 SEC-008 自行重連，不列入確認條件。Core 換 IP 時，預檢要求所有 Agent 已改用網域連回 Core，否則擋下 | 60 秒 |
| 節點的防火牆或網路設定 | 該節點的 Agent 通道 | 該節點的 Agent 重新握手成功；影響 SSH 時，另外要求使用者送出確認 | 60 秒 |
| sshd 設定，以及 sshd 的 PAM 堆疊（含它引入的共用檔，例如 `common-auth`） | 不關閉平台連線 | 使用者送出確認 | 60 秒 |
| 管理入口的監聽位址、Port、平台 TLS（SET-002） | Core 管理入口的瀏覽器連線 | 使用者經新的入口建立新連線並送出確認 | 60 秒 |
| 管理入口的允許來源、入口路徑（SET-003） | Core 管理入口的瀏覽器連線 | 使用者以新連線送出確認 | 60 秒 |
| 管理入口網域 | Core 管理入口的瀏覽器連線 | 使用者經新網域建立新連線並送出確認（考慮 DNS 生效時間） | 10 分鐘 |

影響 SSH 的變更，套用確認倒數會提示使用者「先用新的 SSH 連線登入成功，再按確認」；平台無法驗證這一步，所以只是提示，不是確認條件。sshd 的 PAM 堆疊以外的 PAM 設定依 HSM-011 處理。本規則讓增補 01 T-147 的情境多了自動回復。

## 51.7 刻意不做的事

- 不為每個情境做專屬橫幅或頁面，只新增 51.1 列的五個共用元件。
- 不自動修復漂移，因為現場的狀態可能才是對的。
- 不用 AI 推測異常原因並寫成句子。畫面只呈現能從資料直接得到的內容。
- 不攔截 root 終端機裡的指令。攔不完整，反而給人錯誤的安全感。
- 不把 Cockpit、Webmin 指派為資源的控制者。它們直接改系統檔，沒有可對應的紀錄，硬猜會讓主機資源莫名變成唯讀。
