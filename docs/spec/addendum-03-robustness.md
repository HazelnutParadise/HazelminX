# 規格增補 03｜異常情境的整體處理

- 狀態：已核定（2026-11-07）。
- 位置：接在增補 02（50 章）之後，章節編號 51。需求 ID 以 `ROB-` 開頭，驗收案例 `T-157` 起。
- 範圍：v1.1 已有處理異常的機制，散在不同章節：
  - 控制者與接管：ARC-005、CTR-009、44.1、44.2
  - 現場與平台記錄不同：34.2
  - 資料模型與永久識別碼：34.1、第 7 章
  - 工作引擎與鎖：33 章
  - 告警去重：MON-004
  - 失敗情境：40 章

  本章不重寫這些機制，只做兩件事：
  1. 把它們推廣到所有資源類型，並規定畫面上用同一組元件呈現。
  2. 補上既有規格沒有涵蓋的部分。

## 51.1 原則：用少數機制涵蓋大量情境

逐一為每個怪情況加一個橫幅、按鈕或規則，畫面會越來越吵，實作也會出現互相矛盾的特例。本章把異常歸成六類「系統不確定的事」，每類由一個機制處理：

| 系統不確定的事 | 機制 |
|---|---|
| 誰在控制、資料是不是最新、現在有沒有工作佔用 | 一、資源狀態 |
| 動了它會影響誰 | 二、單一影響圖 |
| 它是正式還是測試用途 | 三、用途等級 |
| 平台自己還能做什麼 | 四、降級模式 |
| 它到底是哪一個 | 五、身分與名稱 |
| 總共有多少、是不是全部 | 六、量的邊界 |

必做的行為一律寫在 51.3 的需求或既有需求裡。51.4 的情境總表只用來證明每個情境都有去處，不另外定義新行為。

畫面上新增四個共用元件：

- **資源狀態條**：資源頁面標題區下方的一列，放控制者、漂移、觀測時間、鎖、用途等級。
- **影響預覽**：寫入前列出受影響對象的面板。
- **降級列**：平台降級時，出現在全站頂端導覽列下方的一列。
- **用途等級徽章**。

其餘畫面沿用既有元件，例如編輯器衝突提示、工作中心、磁碟資訊。

## 51.2 六個機制

### 機制一：資源狀態

細化 ARC-005 與 34.2。「受管資源」指以下類型，機制一與機制二使用同一份清單：

- 節點、引擎環境、磁碟、檔案系統與掛載
- 容器、Compose 專案、服務、儲存卷、網路、映像
- 站點、憑證、Zentinel 入口
- 防火牆規則與對外 Port
- systemd 服務、模組設定、排程
- 資料庫、備份任務
- Kubernetes 資源、權杖

每個受管資源帶以下欄位：

| 欄位 | 內容 | 既有依據 |
|---|---|---|
| 控制者 | HazelminX、某個外部工具（1Panel、Portainer、Webmin、Cockpit、certbot、Helm…）、叢集控制器，或「控制者不明」 | ARC-005 的擁有者欄 |
| 接管狀態 | 唯讀觀察中、已接管、已保留唯讀 | ARC-005、CTR-009 |
| 漂移 | 平台最後套用的設定與現場觀測不一致 | 34.2「現場與平台記錄不同」 |
| 觀測時間 | 資料從現場讀到的時間；預設每 60 秒觀測一次 | UI-007、NOD-007 |
| 鎖 | 目前佔用該資源的工作 | ENG-004、33.2 |

「控制者」就是 ARC-005 的「擁有者」欄位。本章改用「控制者」，是為了不跟 5.1 的「擁有者」角色、增補 02 環境的擁有者（root 或某個 Linux 使用者）撞名。

**寫入規則**

- 控制者是外部工具、叢集控制器或「控制者不明」的資源，平台只能讀取。
- 同一資源偵測到兩個控制者時（例如 certbot 與 Zentinel 都在續同一張憑證），標為「控制者衝突」，並寫出實際生效的是哪一方。在管理員選定控制者之前，平台對該資源只讀（ARC-005：兩個控制器不能同時寫入）。

**漂移的處理**

沿用 34.2 的三個選擇，永遠不自動改回：

- **採納**：平台記錄改成現場的樣子。如果現場的資源已經不存在，平台記錄標為「已在平台外移除」，並保留歷史。
- **還原**：把現場改回平台記錄，走變更計畫與差異預覽。
- **保留唯讀**：接管狀態改為「已保留唯讀」，平台只讀。

**再次接管**

所有資源類型都依 44.2 的程序：先唯讀檢視，記錄原設定，再選擇接管。從 1Panel 移交時，另依 44.1 先停止原工具對該資源的自動排程。

### 機制二：單一影響圖

所有寫入動作在送出前，都從同一份依賴圖算出受影響的對象。既有需求裡各自列影響的地方，改由這份圖提供資料：

- UI-006：設定差異與受影響服務
- SYS-010：重開機
- NOD-008：維護模式
- CTR-005：映像引用
- CTR-007：網路使用
- HSM-003：移除模組前列出引用

**依賴圖的定義**

- 邊有方向，寫成「A 依賴 B」，意思是 B 停止、刪除或設定變更時，A 會受影響。
  - 例如：站點依賴容器，容器依賴儲存卷，儲存卷依賴檔案系統，備份任務依賴儲存卷，對外 Port 依賴容器。
- 節點類型就是機制一的受管資源清單，再加上「工作」。
- 「被引用」指的是：有其他節點依賴這個節點，而且那個節點不在同一次刪除的範圍內。這樣刪除整個 Compose 專案時（UI-009），專案內部的網路不會被自己的容器擋住。

### 機制三：用途等級

用途等級沿用 34.1 的「正式／測試」標記，另外增加「實驗」。標在兩個地方：節點，以及專案環境（34.1 的「專案與環境」，CMP-018 可讓同一個 repo 有多個環境）。

一個資源的有效等級，取它所在節點與所屬專案環境之中較嚴格的那個，順序是正式 > 測試 > 實驗：

- 節點是正式、專案環境是測試，有效等級就是正式。
- 不屬於任何專案環境的資源，只看節點。
- 兩邊都沒有標示時，不顯示徽章，也不改變任何確認流程。

用途等級不改變權限，只影響兩件事：

1. 頁面標題區、資源狀態條與終端機分頁上的等級徽章。
2. 既有的高風險確認框（UI-006）對正式等級的資源，會寫出等級與目標名稱。本機制不新增原本沒有的確認框。

用途等級和增補 02 的「引擎環境」是兩回事：引擎環境是一個 Docker 或 Podman 執行端點。

### 機制四：降級模式

平台自身或依賴的元件壞掉時，依下表決定還能做什麼。不能做的動作停用，並在提示寫出原因。

降級列只在「平台層級」的降級時出現在全站頂端。節點或引擎環境層級的降級，只出現在該節點的頁面與相關資源的狀態條，以免機器一多就永遠掛著降級列。

| 層級 | 壞掉的東西 | 進入條件（預設值，可調） | 解除條件 | 還能做 | 不能做 |
|---|---|---|---|---|---|
| 平台 | 平台資料庫唯讀或損毀 | 連續 3 次寫入失敗，或完整性檢查失敗 | 寫入測試連續 3 次成功 | 讀取；登入照常，但工作階段只存在記憶體，平台重啟後要重新登入；稽核改寫入本機的附加檔案，資料庫恢復後補回；下載診斷包；依 INT-002 用 CLI 救援 | 任何其他寫入 |
| 平台 | 平台資料磁碟剩餘不足 | 平台資料目錄所在檔案系統剩餘 < 5% 或 < 2 GiB | 剩餘 ≥ 8% 且 ≥ 3 GiB | 讀取，以及新增清理類、搬移類工作 | 其他新工作與上傳 |
| 平台 | Core 時間不可信 | Core 與 NTP 的差距 > 60 秒，或無法連到任何 NTP 來源 | 連續 3 次對時成功且差距 < 10 秒 | 全部照常，同時告警 | 暫停「節點時間偏差」判定，顯示「無法判定」，避免把所有節點一起誤判 |
| 節點 | 節點離線 | 超過 90 秒沒有心跳 | 心跳恢復並完成對帳（SEC-008） | 看上次觀測 | 對該節點的寫入 |
| 節點 | 節點時間偏差 | 節點與 NTP 的差距 > 120 秒（以 Agent 回報的對時狀態判定） | 差距 < 30 秒 | 讀取；編輯排程 | 該節點排程的執行、憑證簽發 |
| 引擎環境 | 引擎停止或無回應 | 端點連續 3 次在 10 秒內無回應 | 端點恢復回應 | 依 PKG-006、ARC-001 登入、讀日誌、執行授權的修復 | 該環境的容器操作 |

Core 停止時沒有畫面可以顯示，不屬於本機制。這時的行為依 ARC-002：已運行的網站照常服務，Agent 依 JOB-012 執行預先授權的本地工作。

### 機制五：身分與名稱

- 資源以永久識別碼識別（第 7 章、34.1）。改名、改主機名、換 IP 時保留歷史，畫面顯示曾用名。
- 平台建立的容器帶有該服務的永久識別碼標籤。判定方式：
  - 帶標籤的容器屬於那個服務。平台部署或還原時重建，歷史與告警仍掛在同一個服務上（呼應 WEB-003）。
  - 帶標籤但設定與平台記錄不同，是該服務的漂移（機制一）。
  - 平台記錄的容器不見了，是該服務的漂移，也就是「實例缺失」。
  - 不帶標籤、只是剛好同名的容器，視為新資源，控制者不明，歷史不混在一起。

  所以在主機上 `docker rm` 再 `docker run` 一個同名但沒有標籤的容器，會同時出現兩件事：原服務標「實例缺失」，另多一個新的、控制者不明的容器。
- 名稱類欄位（容器名、檔名、標籤、主機名）一律完整呈現：控制字元以可見符號顯示，非 UTF-8 以替代字元顯示並可檢視原始位元組，超長時換行而不截斷。
- 日誌與檔案內容依 UI-012、FIL-004 的大小上限分段呈現，不受上一條「不截斷」限制。

### 機制六：量的邊界

`/management/v1` 的每個列表端點，以及 UI 的每個表格，都在回應的中繼資料與表格底部寫出每頁筆數、查詢上限與逾時。

- 結果超過查詢上限時，寫出「已顯示 N 筆／總數 M」。
- 逾時時寫「總數未知」，保留已取得的部分，並提供「改成背景工作」，讓同一個查詢以工作的形式在背景跑完，結果在工作中心查看。

## 51.3 要求

| ID | 誰可以做什麼與必要行為 | 可檢驗的完成條件 |
|---|---|---|
| ROB-001 | 維運者可以在每個受管資源看到控制者、接管狀態、漂移、觀測時間與鎖（細化 ARC-005、34.2）。 | 機制一清單內的每種資源都有資源狀態條；漂移列出差異欄位；控制者為外部工具、叢集控制器或「控制者不明」時唯讀；偵測到控制者衝突時，標出實際生效的一方並唯讀，直到管理員選定控制者。 |
| ROB-002 | 維運者可以對任何受管資源的漂移選擇採納、還原或保留唯讀（把 34.2 推廣到所有資源類型）。 | 平台不自動改回；還原走變更計畫與差異預覽；現場已不存在時，採納會標「已在平台外移除」；保留唯讀後依 44.2 可再接管。 |
| ROB-003 | 系統在寫入前，從機制二的單一依賴圖算出受影響的對象並呈現。 | 停止、重啟、刪除、升級、重開機、進入維護、移除引擎、撤銷權杖、改 Port、停用模組都呈現影響，新增的寫入動作也必須接上；被引用的資源，刪除鈕停用並列出引用者；引用者全在同一次刪除範圍內時不擋。 |
| ROB-004 | 使用者可以知道平台與各節點目前是否降級，以及還能做什麼。 | 依機制四的表與預設門檻進入與解除；平台層級出現頂端降級列，節點與引擎環境層級只出現在該節點頁與相關資源狀態條；不能做的動作停用並寫出原因。 |
| ROB-005 | 管理員可以為節點與專案環境標示用途等級（沿用 34.1 的正式／測試，另加實驗）。 | 有效等級依機制三計算，顯示在頁面標題區、資源狀態條與終端機分頁；既有高風險確認框對正式等級資源寫出等級與目標名稱；未標示時不顯示徽章。 |
| ROB-006 | 系統保留資源的名稱、主機名與 IP 歷史，並依機制五區分邏輯資源與執行實例。 | 改名或換 IP 後歷史與告警仍連到同一資源；平台重建的容器掛在同一服務；不帶服務標籤的同名容器視為新資源，原服務標「實例缺失」。 |
| ROB-007 | 使用者看到的名稱類欄位完整且安全。 | 控制字元以可見符號顯示；非 UTF-8 檔名可以顯示、改名、下載並檢視原始位元組；超長名稱換行不截斷。 |
| ROB-008 | 每個列表與查詢宣告其邊界，並在超出時說明。 | `/management/v1` 列表回應的中繼資料與 UI 表格底部寫出每頁筆數、查詢上限、逾時；超過上限顯示「已顯示 N／總數 M」；逾時顯示「總數未知」，保留已取得部分並可改成背景工作。 |
| ROB-009 | 維運者可以看到「看起來還有空間卻不能用」的耗盡狀態（補足 MON-001、STO-001、STO-010）。 | 主機與容器層級監控：PID 使用率、檔案描述元使用率（預設 > 90% 告警）；記憶體壓力用 Linux PSI `some avg60`（預設 > 10% 告警），核心不支援 PSI 時標「不支援」；檔案系統被重新掛成唯讀時告警。容器被 OOM 終止時，事件寫出原因與記憶體限制。需要建檔或寫入的工作，預檢時擋下 inode 用盡或唯讀的檔案系統並寫出原因。 |
| ROB-010 | 可能切斷管理路徑的變更，套用前檢查、套用後確認（細化 SYS-008、SSH-003、SET-002、HSM-011）。 | 管理路徑包括瀏覽器到 Core 管理入口、Core 到 Agent 的通道、維運者的 SSH。防火牆、管理入口 Port 與網域、平台 TLS、sshd、PAM、網路設定，套用前檢查這三條路徑。套用後由變更所在的主機在本機計時（Core 端設定由 Core 主機計時），預設 60 秒內必須收到確認，否則自動回復。確認必須經由套用後新建立的連線送出，例如瀏覽器重新連線、Agent 重新握手、新的 SSH 連線。API 提供確認端點，規則相同。 |
| ROB-011 | 使用者可以從合併後的告警看出抖動程度（細化 MON-004）。 | MON-004 把時間窗內的反覆觸發合併為一個事件時，事件顯示翻轉次數與時間窗；預設時間窗 10 分鐘。 |
| ROB-012 | 系統可以偵測同一主機上的其他管理工具，並標出它們控制的資源（細化 INS-014，從安裝時延伸到持續偵測）。 | 首批支援 1Panel、Portainer、Cockpit、Webmin、certbot；Helm 依 Kubernetes 資源的管理標註判定。依各工具的已知特徵判定，包括 systemd 服務、資料目錄、Compose 工作目錄、容器標籤，判定規則寫在各工具的 adapter。例如 Compose 工作目錄位於 1Panel 安裝目錄的 `apps/` 底下，就判定由 1Panel 控制。判定不出來的資源，控制者標「控制者不明」，不猜。 |

## 51.4 情境總表

「處理」欄指向本章需求或既有需求。「看得到的地方」欄只寫呈現它的元件或頁面，不定義新行為。

### A. 外部變更與多工具共存

| 情境 | 處理 | 看得到的地方 |
|---|---|---|
| 有人用 SSH 下 `docker run／rm` 改了平台管理的容器 | ROB-001、ROB-002、ROB-006（機制五的標籤判定） | 資源狀態條；列表名稱旁的漂移圖示 |
| 有人直接改了主機上的 `compose.yaml` 或 `.env` | ROB-001、ROB-002；34.2；FIL-013 | 專案的資源狀態條 |
| 同主機還在跑 1Panel、Portainer、Webmin、Cockpit | ROB-012；INS-014；44.1、44.2 | 節點頁的元件清單；資源狀態條的控制者 |
| 手動 `apt upgrade` 升了 Docker | NOD-003（依版本顯示可管理能力）；ENV-001 | 節點頁的引擎環境表 |
| 手動編輯 nginx、BIND 等模組設定 | ROB-001、ROB-002；HSM-002 | 模組設定版本 |
| `ufw reset` 清掉平台的防火牆規則 | ROB-001、ROB-002 | 對外 Port 表的資源狀態 |
| `crontab -e` 改了平台的排程 | ROB-001、ROB-002 | 計畫任務的資源狀態 |
| `kubectl` 改了 Helm 管理的資源 | ROB-012；44.2 | 資源狀態條的控制者 |
| certbot 在主機上另外續了同一張憑證 | ROB-001（控制者衝突） | 憑證的資源狀態條 |

### B. 連線、時間與網路

| 情境 | 處理 | 看得到的地方 |

## 51.5 驗收案例

| ID | 情境 | 預期 |
|---|---|---|
| T-157 | 在主機上用 `docker rm` 刪掉平台管理的容器。 | 下一次觀測（預設 60 秒內）該服務標「實例缺失」。提供還原（走變更計畫）、採納（標「已在平台外移除」）、保留唯讀。平台不自動重建。 |
| T-158 | 主機上裝著 1Panel（預設安裝目錄），用 Compose 部署了 3 個應用容器。 | 節點頁的元件清單列出 1Panel；這 3 個容器的控制者標 1Panel 並唯讀，直到依 44.2 接管。 |
| T-159 | 先查看「停止 Zentinel」的影響，再查看「重開機 Zentinel 所在節點」的影響。 | 兩次列出的受影響站點與憑證，包含完全相同的集合。 |
| T-160 | 平台資料庫變成唯讀。 | 出現頂端降級列。可以登入；寫入按鈕停用並寫出原因；可以下載診斷包；稽核寫入本機附加檔，資料庫恢復後補回。 |
| T-161 | 節點標正式、專案環境標測試，對該專案環境部署。 | 有效等級為正式；部署確認框寫出「正式」與專案環境、節點名稱。 |
| T-162 | 節點改主機名並換 IP。 | 仍是同一個節點；顯示曾用名與曾用 IP；舊告警仍連到它。 |
| T-163 | 資料夾裡有非 UTF-8 檔名。 | 可以列出、改名、下載，並可檢視原始位元組。 |
| T-164 | 查詢 1 萬筆容器事件時逾時。 | 顯示已取得筆數與「總數未知」；改成背景工作後，在工作中心看到完整結果。 |
| T-165 | 磁碟空間剩 40%，但 inode 用完。 | 磁碟資訊標出 inode 耗盡；需要建檔的工作在預檢時被擋下並寫出原因。 |
| T-166 | 容器被 OOM 終止。 | 事件寫出 OOMKilled 與記憶體限制，連到該容器。 |
| T-167 | 套用一條會擋掉管理入口的防火牆規則（預設逾時）。 | 套用前警告。從原本仍開著的分頁送確認無效；60 秒內沒有從新連線送出確認，就由該主機本機自動回復。 |
| T-168 | 節點在 10 分鐘內上下線 8 次。 | 合併成一個事件，標出翻轉 8 次與時間窗，不發 8 則告警。 |

## 51.6 刻意不做的事

- 不為每個情境做專屬橫幅或頁面，只新增 51.1 列的四個共用元件。
- 不自動修復漂移，因為現場的狀態可能才是對的。
- 不用 AI 推測異常原因並寫成句子。畫面只呈現能從資料直接得到的內容。
- 不攔截 root 終端機裡的指令。攔不完整，反而給人錯誤的安全感。
